锁定层暂缺席:上一版的"锁定三字段(is_locked/lock_start_time/locked_by)"本轮不接 —— 锁定下线,存储层也没有这些列。本轮存储层只多一个 same_as_candidate_id。未来锁定重启再补锁定字段(那是另一次改动)。

三、查重 → 存储 连接方案

⛔ P0 缺口(必须先补): 查重引擎 IdentityMatchResult(identity-engine.ts:28-36)只返回 {samePerson, matchedRule, needsHumanReview},不含命中对象的 candidate_id;agent 循环命中即 break(candidate-identity-agent.ts:82-90)把 other.candidate_id 丢了。→ same_as_candidate_id 没有来源。这是连接的第一块拼图,不补则后面全断。

3.1 连接三件套(缺一不可)

#改动细节
1 P0引擎补命中 ID 出口给 IdentityMatchResult 加 matchedCandidateId?: string;或在 agent 内联循环命中时显式记 other.candidate_id(更轻,不改引擎签名)。这是 same_as_candidate_id 的唯一来源
2SaveCandidateInput 加字段candidates.ts:32-62 新增 same_as_candidate_id?: string | null(只此一个,不加 lock 字段)
3dedup 档序插第②档candidates.ts:246-281:candidate_id = input.candidate_id ?? input.same_as_candidate_id ?? null;手机号/邮箱档降为 fallback(查重未命中时才用)。命中 same_as → 走既有 UPDATE 分支(COALESCE 刷联系方式),不 INSERT

3.2 Neo4j 一人多简历(已支持,零改 writer)验证

同一人时 saveResult.candidate_id = 老人 ID,后面三点保证"新简历挂老 Candidate node":

  // 1) Resume 写入带老人 candidate_id(allmeta-writers/resume.ts:62)
  writeResumeInstance({ resume_id: 新, candidate_id: 老人, ... })
  // 2) Resume 对象 FK:candidate_id → Candidate(objects_v0_1_015)→ "Resume 归属于 Candidate",天然 1:N
  // 3) Postgres Resume UPSERT key=(candidate_id, object_key)(candidates.ts:364)→ 同一人不同文件 = 多 Resume 行,Candidate 不重复建
结果:同一人 → 复用老 candidate_id,1 Candidate : N Resume,Postgres 与 Neo4j 一致;新人 → 走第⑤档新建。Candidate 绝不重复建。writeCandidateInstance/writeResumeInstance 本身不用改 —— 只要传进去的 candidate_id 是老人 ID。

四、查重 agent 完整流程(内联在 save 之前)

从"独立 agent 收 RESUME_PROCESSED 后跑"改为"resume-parser 在 save-candidate 之前的内联 step compute-candidate-identity"。架构选择:内联(否决独立 agent + 事件串) —— 原子性(解析→查重→保存同一 function retry)、低延迟、避免 Inngest 事件膨胀。

#步骤细节
1构建候选人记录candidateFromResumeProcessed(parsed.data) → rec{name, phone, email, gender, school, major, degree, graduationYear}
2取对比池partnerPgCandidateRepo.findComparisonCandidates(rec) 按 email/姓名/手机尾号预筛 ≤25
3加载规则loadCandidateMatchRules() → IDENTITY-1/2/3(= 本体 9-15 的三级展开)
4逐池 × 逐级比对对每个 other 跑 applyIdentityRules(rec, other, rules, judge);命中即停
5三级(按 priority)① 手机号[exact] ② 姓名[fuzzy]+邮箱[exact] ③ 六字段[4 fuzzy/2 exact] needsHumanReview=true
6 P0记下命中对象 ID命中时 matchedCandidateId = other.candidate_id(当前引擎丢了这个值,必补)
7驱动落库same_as_candidate_id = (samePerson && !needsHumanReview) ? matchedCandidateId : null → 传入 saveCandidate
字段等价(步5 内部):fieldEquivalent 先 exact-normalized;失败且该字段 fuzzy → LLM judge(confidence≥0.8);缺字段 / AI 故障一律保守判不等价。soft-fail:查重异常只落审计,绝不 throw 进招聘管道。

五、抓 9-15 判定 ≠ LLM 自由判(关键澄清)

"通过抓 rule 判断是否同一人" = 抓到结构化三级规则后,用确定性引擎逐字段比对;不是把两份简历整体丢给大模型让它自由裁量。
层谁做是不是 LLM
规则结构(比哪些字段、优先级、客户 scope)数据(rules.json / 本体 9-15)否
命中与否引擎 every(f => f.equivalent)(identity-engine.ts:63)否,布尔确定性
单个 fuzzy 字段的语义等价LLM judge(清华 vs 清华大学、本科 vs Bachelor)是,但仅字段级、且 exact 失败才降级

5.1 抓 9-15 的两阶段(切数据源,不改逻辑)

  • 阶段一(现在,推荐): 引擎继续读 bundled rules.json 的 IDENTITY-1/2/3(source='snapshot')。把 9-15 在本体 processResume 里从"散文"提升为真 step(checkCandidateIdentity,消孤儿、蓝图与代码一致)。这步是本体对齐,不阻塞落库。
  • 阶段二(未来,可选): Neo4j 配齐 Rule 节点后,复用已实现的 fetchRulesViaOntologyApi() 加 ruleType='identity' 分支;切换只改 rules.json metadata.source='ontology-api'(loadCandidateMatchRules 已预留读 source)。

六、锁定 agent 安全下线

现状已等价于下线(已核实):内联 rmhr-lock-check step 受 LOCK_CHECK_ENABLED / CANDIDATE_LOCK_PG_WRITE / LOCK_CHECK_ENFORCE 三 flag 控,.env.local 未设 → 全关 → runLockCheck 直接 proceed('disabled'),不外呼 RMHR、不落库。存储层 INSERT/UPDATE 根本没有 is_locked/lock_start_time/locked_by 列 → 下线对落库零影响。
下线动作(最小)说明
保持三 flag off已是默认;.env.example 标注"锁定 2026-06 暂下线"
解耦 lockOnly → emit 的 gatingresume-parser:455 的 if(!lockOnly) 下线期不应让锁定能抑制下游;rmhr-lock-check step 保留为惰性 no-op(零成本、可秒级重启)。RESUME_LOCKED_CONFLICT 分支随之 dark
ownership agent保留代码(no-context skip),便于未来重启;或从 functions.ts 摘下彻底静默(开放决策)
红线:下线锁定绝不能给 saveCandidate 新增 is_locked/lock_start_time 字段 —— 那是"接锁定进存储",与"下线锁定"矛盾。本轮存储层只接 same_as_candidate_id。

未来重启:仅改三 flag,查重/存储结构零改;rmhr-lock-check step 在位,flag on 即接回(若已解耦 emit gating,重启时重新接 lockOnly → emit 这一处 if)。

七、还没完善的 8 点(逐条处置)

#问题处置(定论)
1 P0引擎缺命中 candidate_id 出口必做:agent 内联命中时记 other.candidate_id(或加 matchedCandidateId)。same_as_candidate_id 的唯一来源
2弱信号(IDENTITY-3 六字段)保守不自动合并:弱信号命中 → same_as_candidate_id=null 走正常 dedup/新建,审计记 linkedCandidateId + dedupAction='pending-review' 留运营复核。误合并代价 > 漏合并
3对比池命中多个老人取 priority 最小者驱动;命中数>1 时审计 conflictingMatches[] 标"库内疑似重复,待人工合并"(库内合并 UI = 开放决策)
4缺手机号/邮箱字段退化保守漏判优于误合并:不自动放宽;仅因某字段缺失而未命中 → 审计记 partial-miss 供复核。默认不加 fallbackIfMissing
5 P0phone-dedup vs 9-15 冲突查重赢:dedup 档序 same_as_candidate_id > 手机号 > 邮箱+姓名;手机号/邮箱仅 fallback。口径="查重前移后,查重是唯一权威归属源"
6一人多简历主字段(覆盖 vs 追加)维持现行 COALESCE(最近非空才覆盖),声明 policy='most-recent-non-empty';Resume 行只追加。append-array / HAS_LATEST_RESUME = 开放决策
7审计可见性扩 selectionNote:linkedCandidateId / matchedCandidateName / dedupAction(auto-merged|pending-review|conflict);/rule-check 页新增"待复核"区 + 可跳转关联候选人
8幂等(同 upload 重放)现状足够:Resume UPSERT 按 (candidate_id, object_key),etag 为空时 resume-parser 自算 MD5。可选加 UNIQUE(candidate_id,etag)
