一、全链路事件流转(6 个在运行 agent)

可视化总览(智能体 × 事件)

文字版(便于检索)

两条业务主线:岗位线(需求→JD)与候选人线(简历→解析→查重/规则检查→匹配→面试邀约)。事件由合作方系统(RAAS)或上游 agent 触发,Inngest 负责派发;每个 agent 独立订阅、互不阻塞。
┌─ 岗位线 ───────────────────────────────────────────────────────────────────┐
│  RAAS:REQUIREMENT_LOGGED / CLARIFICATION_READY / JD_REJECTED               │
│      └─▶ ① JD 生成 ──▶ JD_GENERATED ──▶(发布渠道 → 简历开始回流)              │
└────────────────────────────────────────────────────────────────────────────┘
┌─ 候选人线 ─────────────────────────────────────────────────────────────────┐
│  RAAS:RESUME_DOWNLOADED(新简历落到对象存储)                                  │
│      └─▶ ② 简历解析:下载→解析→[invoke ③ 查重·等结论]→落库(挂老档/新建)→写图谱     │
│                │                                                            │
│                ├─ invoke ▶ ③ 候选人查重(独立函数):调 9-15 规则 → 三级判定      │
│                │     → 落审计 → 返回 same_as_candidate_id(只判定,不操作存储)      │
│                └─▶ 落库完成后发 RESUME_PROCESSED ──▶ ④ 规则检查(按岗位扇出)     │
│                       PASS ▶ MATCH_RULE_CHECK_PASSED ──▶ ⑤ 简历匹配          │
│                       FAIL ▶ MATCH_RULE_CHECK_FAILED(终态,不进匹配)            │
│  注:③ 与 ④ 严格串行,绝不同时进行 —— ③ 在落库前完成(结论决定 candidate_id);     │
│  ④ 在落库后才触发,拿到的已是合并后的最终候选人。两个 rule check 各管一事:        │
│  ③ 查「是不是同一个人」(9-15),④ 查「符不符合这个岗位」(10-x 系列)。             │
│        ⑤ 简历匹配:评分服务打分 ─┬─ ≥40 或无分 ▶ MATCH_PASSED_NEED_INTERVIEW       │
│                                └─ <40 / 调用失败 ▶ MATCH_FAILED(终态)          │
│  RAAS(HSM 审批通过):INTERVIEW_INVITATION_REQUESTED                          │
│      └─▶ ⑥ 面试邀约 ──▶ INTERVIEW_INVITATION_SENT / _FAILED                 │
└────────────────────────────────────────────────────────────────────────────┘

三个要点:(1) 查重是一个独立的、舰队可管理的函数,但以 invoke 方式嵌在简历解析流程里:解析在落库前同步调用它并等待返回结论(图中★),用结论驱动「挂老档还是新建」。查重函数只判定 + 落审计、不做任何存储操作(职责分离:查重=判定,解析=操作);每次调用产生它自己的运行记录(舰队页运行数/成功率/耗时全真实),它下线或失败时解析按「新候选人」降级,主链路零阻塞。判定完成后它还会发出本体预留的 CANDIDATE_IDENTITY_CHECKED 事件(当前无订阅者,蓝图闭环)。(2) 规则检查按岗位(JR)扇出:一份简历投 N 个岗位就做 N 次独立判定、发 N 个事件。(3) 锁定/归属 agent 已于 2026-06-11 下线(开关全关、注册表清出),恢复时只需把 LOCK_CHECK_ENABLED 系列开关打开。

查重是按规则判的,不是自由判断。判定依据是规则库(Neo4j)里的 9-15「同一候选人判定规则」,经「动作 ruleCheckForCandidateIdentity → 步骤 → 规则」这条边抓取(审计里「数据来源:在线规则库」即指此)。9-15 是一条业务散文规则,引擎把它展开成与原文逐字对应的三级结构化比对(① 手机号一致 ② 姓名+邮箱一致 ③ 六字段一致,命中即停)—— 这是确定性执行:精确字段直接比对,大模型只做两件辅助(模糊字段的语义等价判断,如「清华」=「清华大学」;以及把判定依据写成业务文案),不参与、也改不了判定结论。注意一点:三级执行逻辑来自与 9-15 对齐的内置规则快照 —— 在 Neo4j 改 9-15 的文本,审计展示会立即跟着变(实时抓取),但若要改变三级比对本身的逻辑,需同步更新这份结构化快照(散文规则要能执行必须先结构化,这是规则的两种粒度)。

怎么理解「候选人查重」的身份?它是一个被简历解析同步调用的独立智能体(invoke 模式,2026-06-11 定稿)。它是真正独立注册的函数:有自己的规则(从规则图谱抓 9-15)、自己的判定引擎(三级命中即停)、自己的审计署名、自己的运行记录(舰队页可管理、可单独上下线);但它不具备任何存储操作 —— 只做「抽规则 → 判定 → 落审计 → 返回结论」。简历解析在落库前同步调用它并等待结论,拿 same_as_candidate_id 去执行落库(挂老档/新建)。这样三件事同时成立:① 判定发生在落库之前(结论能驱动存储);② 审计与落库出自同一份结论(永不矛盾);③ 它是独立函数,下线/故障时解析自动按新人降级,主链路零阻塞。

事件侧补充:查重函数的触发器是专用事件 CANDIDATE_IDENTITY_REQUESTED(正常链路不发,主路径是被解析 invoke;留作手动复核入口);判定完成后发出 CANDIDATE_IDENTITY_CHECKED(本体 10-3 动作的产出事件,与规则图谱蓝图一致),当前无订阅者,将来有下游要消费查重结论时直接订阅即可。

原文字版(档序细节)

查重不只是「报告重复」,它的结论直接决定落库行为 —— 这是 2026-06-10/11 打通的闭环:
简历解析 (save 之前)
  └─ compute-candidate-identity:resolveIdentityMatch(三级比对,强命中才给 sameAsCandidateId)
       ├─ 强命中(① 手机号 / ② 姓名+邮箱)→ dedup_action=auto-merged → same_as_candidate_id=老候选人
       ├─ 弱命中(③ 六字段)→ dedup_action=pending-review → 绝不静默合并,只标人工复核
       └─ 无命中 → new-candidate → 正常新建
  └─ save-candidate:dedup 档序 same_as_candidate_id 排第二(仅次于显式 candidate_id)
       → 同一人:复用老 candidate_id 走 UPDATE,新 resume 行 + Neo4j Resume 节点都挂老 Candidate(1:N)
       → 不同人:新建 Candidate + Resume

同时,「候选人查重」audit-agent 独立把同一引擎的结论写进规则检查审计(9-15 · 命中第几级 · 关联到谁 · 去重动作 + 大模型生成的判定依据),供 /rule-check 页追溯。引擎是同一个(resolveIdentityMatch 共享),落库与审计永远一致。
