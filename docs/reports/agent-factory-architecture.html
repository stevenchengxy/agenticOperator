AGENT FACTORY v3 · 架构说明

Agent 工厂 是怎么思考、生成 agent 的

不是一条写死的流水线，而是一个自主的 ReAct 大脑(像 Claude Code / Codex)：它读一个业务域的本体,自己推理要造哪些 agent、为每个 agent 现写 prompt、选工具、生成可运行代码,再真实部署到沙箱跑通事件链——跑不通就诊断、修订、重来。全程流式展示思考与每一步操作。

1 两层事件流转

系统里有两条事件流,别混淆:

第一层 · 大脑的推理循环

工厂怎么造 agent —— 一个 LLM 自己在 ReAct 循环里:观察 → 想 → 调工具 → 看结果 → 再决定。下面的环形图就是它。

第二层 · 生成的 agent 的业务事件链

造出来的那些 agent 之间靠 Inngest 事件串联(如 简历下载→查重→解析→规则校验→匹配→邀约)。工厂在沙箱里真实跑这条链来验证。

第一层:大脑的 ReAct 推理循环

正常推进 有问题 → 回去修订 越改越差 → 回滚 验证通过 → 收尾

关键:这不是固定顺序。每一步大脑都根据刚观察到的结果决定下一步——同一个目标,不同的域/状态,工具调用序列可能完全不同。这正是"真智能 vs 表演智能"的区别。

第二层:生成的 agent 的业务事件链(招聘域为例)

触发事件Agent发出事件
RESUME_DOWNLOADED候选人查重CANDIDATE_DEDUP_PASSED
CANDIDATE_DEDUP_PASSED简历解析RESUME_PROCESSED

沙箱里这条链真实部署到 Inngest、真发事件、真跑——reachedTerminal: true 才算验证通过。

3 大脑的工具箱(每一步在干什么)

read_ontology
读这个域的动作/事件/规则 + 工具库;并为每个动作预先匹配好候选工具(suggested_tools)和相关业务规则。这是设计的地基。
create_plan
把"打算造哪些 agent、各自消费/产出什么事件、用哪些工具"写成显式计划,并对照本体校验(防止计划本身就错)。
design_agent
为一个动作现写 system prompt(不套模板)、从工具库选工具、写分支决策逻辑 → 产出 spec + 一份可读 .ts 代码。
validate_graph
静态校验事件图闭合:每个 emit 有人消费、每个 trigger 有人产出、每个 agent 有工具。返回 agentIssueMap——问题绑到具体 slug。
sandbox_run
把生成的 agent 真实部署到 Inngest、真发入口事件、真跑事件链,流式回报阶段(部署→触发→轮询→落定)。
inspect_run
没跑到终态时,看每个 agent 的真实运行细节(状态、卡在哪个 step、决策、错误),用来精准定位要改谁。
refine_agent
针对某个 agent 迭代修订(保留 attempt 历史 + critique,不是覆盖);修订后自动评分对比上一版。
revert_refine
如果 refine 之后分数退步,直接回滚到上一版,换角度再想——而不是硬塞。
analyze_failure / finish
收尾时把根因/经验写成结构化反思,存进 FailureReflection——下次为这个域生成时自动注入到系统提示(跨次学习)。
web_search / spawn_subagent / create_skill
联网查业务规则;子问题派隔离子大脑深入;发现可复用模式(如"三级去重")织成技能注入后续 agent。

4 它怎么"思考"

观察驱动

每一步根据上一步的真实结果决定下一步,不是按清单走。

边想边说

调任何工具前先把分析作为消息流式输出(角色/边界/选工具理由/决策推导),用户能实时看到思考。

跨次学习

每次结束留下反思 → 下次同域生成时自动注入系统提示。同一个域越跑越稳。

5 它怎么调工具(工具接地)

工具是人工提前编好的(封装 RoboHire / RAAS / MinIO / Allmeta 等真实接口)。大脑只选用,但 LLM 常凭空造名字(parseResumeFile),对不上命名空间真名(robohire.parseResume)。三道接地保证 agent 不会"光有 prompt 没有手":

① 预匹配read_ontology 时按动作语义把真实工具库预匹配成 suggested_tools,递给大脑选——从源头给真名。
② 模糊解析保守的 token-superset 匹配:parseResumeFile → robohire.parseResume,但绝不误绑不存在的工具(如黑名单工具)。
③ 兜底 floor大脑选少了(≤1 个),按高相关工具库自动补到"读→算→写"一套,预算无关。
④ 约束解码design_agent 的 action/tools 字段锁成真实名字的 enum——凭空造的名字直接生成不出来。

效果:生成的 agent 工具解析率 0 → 100%,绑的都是正确真工具。

6 它怎么判断"要重新生成 / 修订"

大脑有多个明确的触发点来决定回去改,而不是一次过:

信号来源动作
事件图不闭合validate_graph 返回 agentIssueMap对有问题的 slug 直接 refine_agent(不靠文本猜)
沙箱没到终态sandbox_run + inspect_run看清哪个 agent 卡住 → 针对性 refine
修订后分数退步refine 自动 score 对比(Δ ≤ −10)警告 → revert_refine 回滚,换角度
反复磨同一个 agentper-agent refine 预算(>3 次)拒绝继续 refine,提示回滚/接受/重规划
有动作没造 agentfinish 时的覆盖闸口拒绝 finish 并点名缺口;累计到上限才用降级占位兜底(绝不静默漏)

7 质量护栏总览

工具接地
每个 agent 绑真实工具(解析率 100%),不会是空壳。
rule-check 动态抓规则
规则校验 agent 实时从本体抓规则(fetchOntologyActionRules),不烤进 prompt(规则会变、有上百条)。
自动评分 + 退步检测
每次 refine 量化 4 个维度对比,退步即警告/回滚。
覆盖闸口 + refine 预算
不漏 agent、不无限磨;到底线用显式降级占位,绝不假装完成。
独立审查
确定性检查多分支未覆盖/工具未接地/降级占位,加 LLM 判官只查"规则有没有真编进去"。
可读代码 + 可追溯
每个 agent 生成一份可读 .ts 代码可看可改;整条 transcript 落库,刷新/历史可回看。

8 生成出来的 agent(以 rule-check 为例)

每个 agent 既有 LLM 现写的 prompt,也有一份可读的 Inngest 函数代码。规则校验 agent 动态抓规则:

// ruleCheckForMatchResume — 由 Agent 工厂从本体动作生成
import { inngest } from '@/server/inngest/client';
import { fetchOntologyActionRules } from '@/lib/ontology-rules';
import { chatComplete } from '@/server/llm/gateway';

export const ruleCheckForMatchResumeAgent = inngest.createFunction(
  { id: 'agents-generation-rule-check', triggers: [{ event: 'RESUME_PROCESSED' }] },
  async ({ event, step }) => {
    // 实时从本体抓本动作该执行的业务规则(不写死)
    const rules = await step.run('fetch-rules', () =>
      fetchOntologyActionRules('ruleCheckForMatchResume', 'Agents-generation'));
    const decision = await step.run('reason', () =>
      chatComplete({ system: SYSTEM_PROMPT, user: JSON.stringify({ rules, ...event.data }) }));
    return decision.pass
      ? step.sendEvent('emit', { name: 'MATCH_RULE_CHECK_PASSED' })
      : step.sendEvent('emit', { name: 'MATCH_RULE_CHECK_FAILED' });
  },
);
