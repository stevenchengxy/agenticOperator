01 · 结论摘要

当前 Agentic Operator 的 Agent 工厂 v3，本质上已经从“提示词生成器”进化成了一个 Harness-first 的自治生成系统：一个 ReAct 风格的 Brain 在 SSE 中流式运行， 通过受控工具读取 live ontology、规划 agent、设计 spec、生成可审阅代码、做静态验证、 部署到 sandbox domain、观察 Inngest run/archive，再根据失败原因 refine，最后只有在满足严格 finish gate 时才把草稿同步到 AgentVersion。

但它现在还不等价于“所有 agent 都必须由 AI 生成代码并直接执行”的工厂。更准确的判断是： v3 会要求 LLM 生成完整 TypeScript agent 代码作为可审阅产物，但当前通用生成域的实际运行路径仍然是 AgentVersion spec + generic executor，并不是直接执行这段 AI 生成的 .ts。对简单事件路由型 agent，这条 spec-runtime 路径是安全和确定性的特性；真正需要补齐的是 “什么时候继续用 spec executor，什么时候升级到 Behavior.compute / CodeAct-style code action”的显式选择器。

一句话判断： 现在的系统是“可观察、可沙箱验收的 Agent 生成 Harness”。下一步不该把路线写成 A/B 二选一，而应以 AgentContract/EventContract 统一三类 runtime： 简单 agent 走 spec executor，复杂业务逻辑走 Behavior.compute， 需要多工具控制流/数据流的少数 agent 才进入 out-of-process CodeAct-style sandbox。
强项 ReAct brain + deterministic tools + sandbox evidence + finish gate，方向非常正确。
最大短板 runtime selector 未显式化、成本治理未产品化、trace 未规范化、gold-standard 还没接入 finish。
最优路线 先用 AgentContract 统一 A/B/CodeAct，再按复杂度混合 runtime，谨慎引入直接代码执行。

2026-06-25 增量分析：Agent 工厂已经进入 Multi-Harness 阶段

相比上一版分析，当前仓库已经发生了一组关键升级：Agent 工厂不再只是 v3 单 brain 生成链路， 而是在向 ChatOps + Tool-Smith + Agent Registry + Meta-Orchestrator + Gold Standard 的多 harness 系统演进。很多我们昨天标成 gap 的点已经部分落地，但核心分叉仍然存在： 最终运行的通用生成域 agent 仍主要通过 spec + generic executor 执行，而不是直接执行 AI 写出的 TypeScript。 这不必被视为缺陷本身；真正需要补的是 runtime selector：按 agent 复杂度决定 spec executor、Behavior.compute 或 CodeAct-style sandbox，并让它们都实现同一个 Agent/Event 合同。

进一步核验后，lib/agent-factory-v3/contract.ts 已经把 inputSchema / outputSchema 组装成一等 AgentContract / EventContract，并接入 validate_graph 做 payload 对账。也就是说，原报告里的 “Contract Graph 缺位” 已经变成 “P0-1 基础能力已落地，下一步要扩展到 runtime selector、finish gate 和部署治理”。

2. 当前真实架构的新判断

系统已经更像简化版 Codex/Claude Code

现在有连续聊天、持久 HITL、工具调用 trace、计划 artifact、sandbox 进度、可回看 run history。 这意味着产品形态已经从“一次性 agent 生成表单”转向“人机协同构建环境”。

但 runtime selector 还未产品化

codegen_agent 生成的 TypeScript 通过了语法、import allowlist 和事件接地校验， 但通用生成域实际运行仍由 executeGeneratedAgent(spec) 决策并发事件。AI 代码目前仍偏审阅/证明 artifact； 需要把每个 agent 的 runtimeDecision 记录成一等 artifact。

“先复用再生成”是正确方向

Agent Registry 把真实 handwritten agents 和 generated agents 放进同一选择空间， Meta-Orchestrator 可以只为缺口动作调生成 harness。这样比每次全量重造更省、更稳。

Tool-Smith 是关键能力，但要治理

让 AI 从文档生成声明式 HTTP 工具，是扩展外部平台能力的好路径。下一步重点不是“让它更自由”，而是审批、版本、测试、回滚和运行审计。

CodeAct 校正：不是 A/B 二选一，而是契约统一的混合 Runtime

Claude 对这一点的批评是成立的：CodeAct 论文的核心洞见不是 “最终交付的业务 agent 一定要变成 TypeScript 源码”，而是 runtime agent 的动作空间 可以从 JSON/tool-call 扩展为可执行代码。代码 action 原生支持变量、循环、条件和多工具组合，复杂任务下可以减少 action hop，并让报错成为自我 debug 的观察信号。

因此，对 Agentic Operator 更准确的路线不是“spec executor 或 Agent-as-code 选一个”，而是： 统一 AgentContract/EventContract，按 agent 复杂度选择 runtime substrate。 简单业务节点继续走声明式 spec executor；需要可维护业务逻辑的节点生成 Behavior.compute； 少数需要多工具组合、循环试错、数据流编排的节点才进入 CodeAct-style out-of-process sandbox。

Runtime lane 选择条件 优势 硬性边界
A · Spec Executor 触发事件明确、输出事件枚举明确、工具少、无需复杂循环/状态机。 最安全、最容易审计；适合大多数事件路由和简单业务判断 agent。 必须通过 AgentContract/EventContract payload 对账；degraded policy 要显式。
B · Behavior.compute 有较复杂业务规则、需要可读可测代码、需要团队 review 和长期维护。 工程资产清晰；可运行 typecheck、unit tests、contract tests。 仍不能同进程执行未审计 AI 代码；需要 isolated compile、依赖白名单和 PR-style review。
C · CodeAct-style Sandbox 需要多工具组合、循环、变量复用、错误驱动自我修复；JSON action hop 明显太多。 表达力最强，最符合 CodeAct 对复杂 action space 的发现。 必须 out-of-process / microVM，限制网络、文件系统、依赖、secret、wall time 和 action budget。

对原报告的修正

“AI 写的 .ts 不是当前运行代码”不是天然头号缺陷。对简单业务 agent，声明式 spec runtime 反而是可控特性。 缺口在于 runtime 类型没有被明确记录、解释、验证和展示。

CodeAct 强化的安全结论

如果引入可执行代码 action，绝不能同进程 import 或 eval。CodeAct 论文也把 sandbox breakout 列为需要更强安全机制的风险。 因此 Lane C 必须比现在的 codegen gate 更强。

对 gold-standard 的新增指标

CodeAct 的 M3 ToolEval 思路提醒我们：复杂 agent 不只看“最后有没有跑通”，还要看 action 效率。 建议给 gold-standard.ts 增加以下维度：

  • actionsToTerminal：从入口事件到终态用了多少 agent/tool/code action。
  • toolHopCount：为了完成同一业务目标调用了多少外部工具。
  • selfDebugTurns：失败后自我修复多少轮才收敛。
  • naturalChainEfficiency：自然链路证据与 coverage-pass 证据分开计分。

2026-06-26 复核：Agent 工厂正在从生成器变成 ChatOps 控制平面

这次代码变化很大，架构判断需要再更新一次。当前系统已经不只是“输入目标 → 生成 agents → 沙箱跑一遍”的生成器， 而是在变成一个 聊天式 Agent 工厂控制平面：它能先判断用户意图，回答信息性问题，继续同一场对话， 运行中接受人工介入，把 brain run 和 conversation checkpoint 持久化，展示成本计量、工具库、事件合同、沙箱证据和历史回放。

Agent 双平面架构：Harness Agents 与 Product Agents 必须分治

这里需要先把“agent”这个词拆开。当前系统里至少存在两类性质完全不同的 agent： 构建/运行过程中的 Harness Agents，以及 最终交付的业务流程 Product Agents。 它们都可以“思考、调用工具、甚至派生 sub-agents”，但它们的目标、权限、记忆、验收和部署生命周期完全不同。 如果不分治，系统会很快变成：构建工具、业务 agent、subagent、Inngest function、tool wrapper 混成一个概念，后续很难治理。

核心原则： Harness Agents 可以创造、修改、验证 artifact；Product Agents 只执行业务流程合同。 Product Agents 即使拥有自己的小 harness，也必须被 AgentContract 约束在单次业务运行、预算、工具权限和输出事件内。

级别 Product Agent 内部能力 适用场景 必须加的限制
L0 · Function Agent 固定逻辑或一次 LLM decision；不使用工具或只读少量上下文。 格式转换、简单分支、状态同步。 输入/输出 schema、幂等键、重试策略。
L1 · Tool-Using Agent 单 agent 内 ReAct，小步调用允许工具，最后 emit 一个合同事件。 简历解析、候选人查重、规则校验。 maxIterations、allowedTools、dry-run/live-write policy、degraded policy。
L2 · Delegating Product Harness 可派生 sub-agents 辅助研究、检索、评分或并行判断，但最终仍由父 agent 负责一个业务输出。 复杂匹配、跨系统调查、需要多视角评审的业务节点。 maxSubagents、maxDepth、subagent tool scope、预算、trace、禁止修改工厂 artifacts。
L3 · Builder Harness 可生成/修改 agent、tools、skills、contracts、tests。 Agent 工厂、Tool-Smith、Meta-Orchestrator、Verifier。 只能在构建平面运行；写入 artifact 必须 trace + gate + human approval。
建议： Product Agents 默认只能到 L1。只有当某个业务节点确实需要“运行时派生 sub-agents”时，才在 AgentContract 中显式声明 harnessLevel: "L2"、maxSubagents、maxDepth、allowedSubagentTools。 L3 永远属于构建平面，不应混进交付流程。

3. 对当前代码抽象的建议修正

当前 lib/agent-harness/types.ts 已经有 AgentKind = "builder" | "product" | "harness"、 AgentExec 和统一 Runner。这个方向很好，但建议进一步把“平面”和“是否能 spawn”拆开： harness 更像能力等级，不应与 builder/product 并列成第三种实体。 

type AgentPlane = "builder" | "product";
type AgentSubstrate = "in-process" | "inngest" | "tool";
type HarnessLevel = "L0" | "L1" | "L2" | "L3";

type AgentNodeContract = {
  id: string;
  plane: AgentPlane;
  substrate: AgentSubstrate;
  harnessLevel: HarnessLevel;
  triggerEvents: EventRef[];
  outputEvents: EventRef[];
  allowedTools: string[];
  canWriteArtifacts: boolean;      // true only for builder plane
  canSpawnSubagents: boolean;
  maxSubagents?: number;
  maxSpawnDepth?: number;
  memoryScopes: Array<"conversation" | "artifact" | "event" | "business-db" | "run-archive">;

};

4. 运行时桥接：统一 Runner 可以保留，但 Policy 必须先判定

统一 invoke(node,input) 是好抽象，因为 UI 和编排器不需要关心底层是 tool、in-process sub-brain 还是 Inngest。 但在真正执行前，Runner 应先做 policy resolution：

  • 如果 plane="builder"，允许访问 artifact workspace，但高风险写入需要 gate。
  • 如果 plane="product"，只能访问 event payload、业务 DB、允许工具和 run-local memory。
  • 如果 product agent 要 spawn subagent，subagent 继承父 runId、budget、traceId，且不能写工厂 artifact。
  • 如果 agent substrate 是 Inngest，必须通过 EventContract parse/validate 输入输出。
  • 如果 agent substrate 是 in-process，必须有 wall-clock、turn、token、spawn depth 限制。

5. 报告级结论

可以统一描述，但不要统一权限

所有 agents 都可以进入 Agent Registry 和 Runner，但必须带上 plane、 substrate、harnessLevel 和 policy。统一调用不代表统一治理。

Product Agents 不能偷偷变成工厂

业务流程 agent 可以思考和派生 helper，但不能在业务运行中随意生成新的生产 agent、改 tools-library 或改 EventContract。 如果业务需要动态生成流程，那应该是一个明确的 Builder workflow，并有人审。

智能化机制深潜：它为什么不是固定流水线

Agent 工厂的“智能化”不应该被理解成“LLM 输出了一段长推理”。真正的智能化来自一个闭环： 任务理解 → 上下文装载 → 计划 artifact → 工具/子脑/技能选择 → 观察真实反馈 → 修改计划或 artifact → 沙箱验证 → 反思沉淀。 当前代码已经把这套机制分布在 Factory Brain、Meta-Orchestrator、Selection Harness、Tool-Smith、Skills Library、Sandbox 和 Trace UI 里。

05 · 运行时真相：AI 代码与实际执行路径并不相同

这是目前最值得产品和工程团队对齐的一点。v3 finish gate 要求每个 spec 都有 codeSource="ai" 和 generatedCode，但对于通用生成域，sandbox 和真实 shell function 运行的是 executeGeneratedAgent 解释 spec 后调用 LLM 做分支决策。AI 生成的 TypeScript 更像“可审阅的目标代码/设计证明”，不是当前被执行的生产 artifact。 这对简单 agent 并不坏；它提供了更可控的默认运行时。真正需要补的是把这个事实显性化，并允许复杂 agent 升级到其他 runtime lane。

技术细节深潜：Memory、Skills、通信与运行闭环

这一节把 Agent 工厂拆到更细的工程机制。重点结论是：当前系统已经有多层“记忆”和通信介质， 但它们分散在 message history、BrainCtx、文件系统技能库、数据库反思、Inngest archive 和 AgentActivity 中； 下一步应该把这些能力产品化为可查询、可恢复、可评测的工程资产。

1. Memory 管理：热上下文、结构化状态与长期沉淀

Memory 层 当前实现 优势 不足与优化
热上下文 messages[] 持有 system、goal、assistant tool calls、tool results；每轮发给 gateway。 简单直接，ReAct loop 可连续推理。 成本随轮次增长；应把 token/cost 做成可观测指标、软阈值和确认门，并把每轮输入输出落到 normalized trace。
结构化工作记忆 BrainCtx 保存 specs、plan、attemptHistory、lastSandbox、lastValidation、humanDirectives、rules/tools。 这是最可靠的“权威状态”，不靠 LLM 自己记。 应把它序列化为 run checkpoint，支持 route 重启后恢复。
自动压缩 超过约 120k chars 后，保留 system/goal、最近 6 个 tool-call turns，中间替换成 deterministic summary + LLM 摘要。 很接近 ReSum/AgentFold/ACON 的思想，且 deterministic summary 防止关键状态丢失。 需要 summary loss audit：校验 coverage gap、last failure、run ids、human directives、sandbox fingerprint 是否都保留。
跨 run 反思 FailureReflection 写入 kind/summary/rootCause/lesson，后续同域 run 前 8 条注入 system prompt。 低成本实现 Reflexion 风格 verbal memory。 应加适用条件、过期策略、冲突检测和效果评估，避免旧 lesson 污染新 ontology。
程序性记忆 skills-library 用文件系统保存可复用 promptFragment、tools、decisionRule、useCount。 人可读、可 git diff、可跨域复用。 需要 skill lint/test/versioning，不然技能会从经验沉淀变成隐性 prompt debt。

2. Skills 生成与复用：从一次经验到可沉淀能力

Skills 当前不是 Codex 外层技能系统，而是 Agent Factory 自己的“agent 设计 know-how”：由 brain 在运行中调用 create_skill 写出，再在后续 use_skill 调入本轮，最终由 design_agent 织入生成 agent 的 system prompt。

Skill 字段 现在的作用 需要补强
promptFragment 直接织进 agent 的 system prompt，是技能最核心的行为指导。 加 lint：禁止过泛、禁止事件名过时、必须引用适用 action/object/rule。
tools 作为推荐工具进入 buildSpecFromAction，但只有 registry 中存在的工具会留下。 加工具适配测试：skill 推荐的工具是否真的适用于该 action 的输入对象。
decisionRule 一句决策规则，补足 prompt 中的分支判断。 改成结构化 rule：condition、positive event、negative event、evidence required。
domain / * 控制本域复用或跨域复用。 跨域技能需要更严格，建议有 domain compatibility 标签和人工 review。
useCount 排序信号，复用越多越靠前。 不能只看次数，还要记录“复用后 sandbox 是否变好”的 success rate。

3. Agents 之间通信：事件总线，而不是直接对话

这里要区分两类“agent 间通信”：一类是工厂生成期的 Brain ↔ Subagent， 另一类是运行期的 Generated Agent ↔ Generated Agent。目前二者机制完全不同。

通信类型 当前机制 好处 风险与建议
运行期 agent → agent Inngest namespaced event：上游 step.sendEvent("emit", { name: `${domain}/${event}` })，下游监听同域 event。 天然异步、可重试、可观察，适合业务流程链。 补 payload schema version、correlation contract、dead-letter/replay UI；避免只靠自由 JSON payload。
运行期 agent 内部决策 executeGeneratedAgent 绑定 registry tools，最后必须调用 decide 从 emit enum 选一个事件。 把自由文本收敛为事件决策，适合事件驱动流程。 degraded fallback 已在 sandbox gate 拒绝，但生产策略也应显式记录，不应静默走首分支。
生成期 main ↔ subagent spawn_subagent 启动隔离 runBrain，只给 read-only tools + web_search，最后回传 summary。 能做独立研究，不污染主 ctx，也不能部署或改 agent。 summary 是有损压缩；建议保存 subagent trace、task spec、evidence refs 和 token budget。
人类 → brain /api/factory-v3/brain/inject 写入 in-process mailbox，conductor 下一 turn drain 成 authoritative user message。 SSE 单向流有了回程通道，且 humanDirectives 会进入 compaction summary。 进程重启会丢；生产化应改 DB-backed directives，并显示在 run timeline。

4. Tool Grounding、Sandbox 与闭环控制

Tool grounding

read_ontology 输出 availableTools、suggested_tools、dataObjects； schema-grounding 尽量用 enum 约束 action/tool 名；buildSpecFromAction 解析 LLM 选择的工具，找不到的进入 unresolvedTools，不会静默假装存在。

建议：加 tool compatibility checker，验证工具输入对象、sideEffect、dryRun 支持和 action intent 是否一致。

Sandbox evidence

sandbox_run 会把 specs 部署到 sandbox-<domain>，触发入口事件， 通过 archive 观察 runs/events，并把 lastSandbox 存成带 fingerprint 的一等状态。 finish 要求当前 specs 与 sandbox fingerprint 一致。

建议：把每次 sandbox evidence 独立落表，支持按 agent/step/event replay 与 diff。

Loop control

Brain 有 MAX_TURNS=200、finish refusal 警告、refine attempt history 和自动 compaction。 你们已经选择不靠 token 硬上限截断长程工作；因此治理重点应转向成本可视化、软阈值、确认门、sandbox run cap 和可审计预算状态。

建议：加 per-run/per-tool/per-subagent 预算和 interrupt policy，超预算时要求 analyze_failure 而不是继续试。

目标态改造蓝图：ChatOps Agent Builder

如果目标是“最终生成能运行、能部署到 Inngest 的 agents”，那 Agent 工厂就不应该只像一个生成器， 而应该像一个简化版 Claude Code / Codex：用户用聊天提出目标和约束，AI 自主阅读上下文、给计划、执行工具、 修改 artifact、部署到 sandbox、观察失败、修复，再把可验证证据交给人批准。关键是： 聊天是交互界面，contract/code/tests/deploy evidence 才是系统事实源。

北极星： 每次 build run 的最终产物不是一段回答，而是一组版本化 artifact： AgentContract[]、EventContract[]、可编译的 agent implementation、Inngest adapter、 golden tests、sandbox run evidence，以及可 promotion 的 AgentVersion。

1. 把“可运行 Agent”定义成三段式 artifact

层 职责 AI 可做什么 人在哪里介入
Contract 定义 agent 接收什么事件、输入 payload schema、可发出哪些事件、每个输出 payload schema、工具权限、重试/幂等/副作用策略。 从 ontology 和用户目标推导 contract graph，指出不确定处，生成 JSON Schema。 批准关键业务合同：事件名、payload 字段、失败分支、人审 gate、外部副作用。
Implementation 实现业务判断：读取输入、调用工具、产出 typed decision。建议形态是 Behavior.compute(input, ctx)。 写 TypeScript、补测试、根据 sandbox 失败 patch。 审阅高风险逻辑、规则解释、合规/风控阈值。
Inngest Adapter 稳定外壳：createFunction、trigger 绑定、event parse、step.run、sendEvent、日志、AgentActivity。 一般不需要自由生成，可由 deterministic generator 从 contract 生成。 批准部署目标：sandbox、draft、active。
推荐选择： 不要让 LLM 每次自由生成整段 Inngest boilerplate。更稳的方式是： AI 生成 AgentContract 和 Behavior.compute； 系统用确定性模板生成 Inngest adapter。这样最终仍是可运行 TypeScript/Inngest agent， 但部署边界、日志、重试、dry-run、schema parse 都由平台保证。

2. Agent I/O Contract：先规定通信合同，再写 agent

Agent 之间不能只靠 prompt 里写“发出某事件”。应把每个事件和每个 agent 的输入输出升级为可验证合同。 合同一旦进入 build run，AI 修改它必须生成 diff 和理由；高风险合同变更需要人批准。

type AgentContract = {
  actionName: string;
  triggerEvents: Array<{ event: string; version: number }>;
  outputEvents: Array<{ event: string; version: number; when: string }>;
  inputSchema: JsonSchema;
  decisionSchema: JsonSchema; // event enum + payload per event
  tools: Array<{ name: string; required: boolean; sideEffect: "none" | "dry-run" | "external" }>;
  idempotencyKey: string;
  retries: number;
  timeoutMs: number;
  humanGate?: { event: string; requiredFor: string };
};

3. 聊天式 AI Builder Loop

交互体验上，用户看到的是聊天；系统内部应该是一个明确状态机。AI 的“自主思考”不要只体现为长文字， 而要体现为可审计的 plan、工具调用、artifact diff 和 evidence。

阶段 AI 行为 人类介入 系统状态
Understand 读取 ontology、registry、历史 reflection/skills，提出理解摘要和风险点。 补充业务目标、禁区、上线范围。 BuildBrief、ContextPack
Plan 生成步骤化计划：contract -> code -> tests -> sandbox -> repair -> promote。 批准计划或改优先级。 BuildPlan 每步有状态、证据要求和预算。
Contract 生成/修改 AgentContract 与 EventContract，展示 diff。 批准 input/output、事件名、payload 字段、人审 gate。 ContractGraph frozen 或 draft。
Implement 生成 Behavior.compute、测试、fixtures，运行 typecheck/test。 审阅高风险业务逻辑。 AgentSource、TestSuite、TraceEvent
Verify 部署 sandbox Inngest app，触发 golden scenarios，inspect run archive。 指导失败修复方向，确认是否接受边界风险。 SandboxEvidence、RegressionScore
Promote 总结差异、证据、风险，准备从 draft/sandbox promote。 最终批准 active deploy。 AgentVersion draft -> active。

4. Builder 工具集应从“生成工具”升级为“工程工具”

工具 作用 为什么需要

5. Lane B 代码目标形态：Behavior.compute + Inngest Adapter

对需要代码资产的复杂 deterministic agent，这样做可以兼顾“AI 自主写业务逻辑”和“平台稳定部署”。 AI 不需要每次记住所有 Inngest 细节；它只需要实现输入到输出 decision 的核心逻辑，adapter 负责平台一致性。 简单 agent 不必强行升级到这个 lane。 

export type AgentDecision<E extends string, P> = {
  event: E;
  payload: P;
  reasoning: string;     // 可审计摘要，不要求暴露完整内部推理
  confidence: number;
};

export interface AgentBehavior<Input, Decision> {
  compute(input: Input, ctx: {
    tools: ToolRegistry;
    dryRun: boolean;
    log: AgentLogger;
  }): Promise<Decision>;
}

// Deterministic adapter generated from AgentContract
export function makeInngestAgent(contract: AgentContract, behavior: AgentBehavior<unknown, AgentDecision<string, unknown>>) {
  return inngest.createFunction(
    { id: contract.actionName, name: contract.actionName, retries: contract.retries },
    { event: contract.triggerEvents.map((t) => `${contract.domain}/${t.event}`) },
    async ({ event, step }) => {
      const input = parseWithSchema(contract.inputSchema, event.data);
      const decision = await step.run("compute", () => behavior.compute(input, runtimeCtx));
      parseWithSchema(contract.decisionSchema, decision);
      await step.sendEvent("emit", {
        name: `${contract.domain}/${decision.event}`,
        data: { _runId: event.data._runId, source: contract.actionName, ...decision.payload },
      });
      return decision;
    },
  );
}

6. 人工介入应该是“指令对象”，不是临时消息

现在 HITL mailbox 已经从进程内队列升级为 DB-backed 回程通道，但目标态还要把人工介入进一步结构化。每条人工指导应该有 scope， 比如全局、某个 agent、某个 event contract、某个测试场景或发布动作。AI 必须在后续计划里标记它如何遵守， 或为什么阻塞。

Directive Scope 例子 系统行为
global “这个域不要调用真实外部 API，只允许 dry-run。” 所有 tool/deploy action 自动继承，违反时拒绝执行。
agent “ruleCheck agent 必须 fail-close。” 写入 AgentContract 和测试用例，sandbox 验证失败分支。
event “MATCH_FAILED payload 必须包含 reasonCode。” 修改 EventContract schema，影响 producer/consumer。
test “加一个缺少学历字段的简历样例。” 生成 golden fixture，并纳入 finish gate。
deploy “先只部署 sandbox，不要 active。” promote 工具被锁住，直到用户解除。

Step 1 · Contract-first

  • 新增 EventContract / AgentContract。
  • UI 展示 contract graph 和 diff。

Step 2 · ChatOps Workspace

06 · 当前优势

Harness-first 方向正确

v3 不把生成结果直接当真，而是通过工具、图验证、sandbox 和 finish gate 逐层收紧。这个方向比“更大 prompt”可靠得多。

Live ontology grounding

read_ontology 强依赖 live Allmeta/registry，避免在陈旧快照上部署，这是控制平面系统很重要的保守性。

可观察 ReAct loop

Brain event 把 think、tool call/result、plan、inspect、validation、score、done 都流给 UI，使用户能看到 agent 工厂如何自我修复。

沙箱证据不是装饰

sandbox_run 会部署 dedicated domain、触发 entry event、读取 archive 和 AgentActivity，并用 fingerprint 防止旧结果被复用。

失败反思可跨 run 复用

FailureReflection 把失败根因和 lesson 注入后续 brain prompt，接近 Reflexion 的 verbal memory 机制。

原子化发布

finish 前不把最终草稿写入 fleet，能避免半成品污染 active/draft 版本；这是合理的生产安全默认值。

07 · 不足与风险清单

以下按生产影响排序。P0 是会阻碍“可信自动生成并上线”的关键问题；P1 是会显著影响规模化使用的工程问题； P2/P3 是体验、效率和治理问题。

优先级 问题 为什么重要 建议修复方向
P0 Runtime selector 未显式化 代码生成产物与实际执行路径分离本身可接受，但如果不记录 runtimeDecision，审计边界和部署策略会变模糊。 按复杂度生成 runtimeDecision：spec-executor / behavior-code / codeact-sandbox；三者都必须实现同一 AgentContract/EventContract。
P0 成本可观测与策略门未闭环 你们已选择不做简单 token 硬上限；因此更需要把 LLM、subagent、Tool-Smith、web/doc fetch 的成本和耗时变成可见、可确认、可审计的状态。 增加 cost meter、soft threshold、用户确认门、per-subagent/tool/doc-fetch 策略，并把消耗写入 normalized trace。
P1 Golden harness 已启动，但还需产品化 gold-standard.ts 已能对标招聘真实 agents 的签名/分支/工具；但它还未成为所有域的 finish gate，也缺 N-run 稳定性与 mutation tests。 把 gold score 接入 FactoryV3 eval；为非招聘域建立 golden fixtures；加入 branch mutation、N-run variance 和 regression score。
P0 Sandbox 隔离仍偏软 当前 AI 代码未直接执行，所以风险可控；但若未来执行 codegen 产物，仅 TS transpile 不是安全边界。 先 out-of-process worker，再考虑 Firecracker/gVisor 级隔离；加 import allowlist、network/fs policy。
P1 v3 trace 未规范化 v3 主要存 monolithic transcript JSON，虽然 UI 可看，但难以查询每次 LLM/tool 输入输出、成本、父子关系和 replay。 新增 normalized FactoryTraceEvent/FactoryLlmCall v3 版，保留 JSON transcript 只做展示缓存。
P1 Context compaction 仍是启发式 长程 agent 会出现 context rot；当前靠阈值和总结，容易丢失关键约束或失败细节。 把状态拆成 deterministic state、retrievable event ledger、LLM summary，并做 summary loss audit。
P1 代码验证已加强，但还未到可执行发布级 新版本加入 import allowlist 和事件接地校验，这是明显进步；但仍主要是语法/静态字符串级检查，不等于隔离项目完整 typecheck/test。 在临时项目中运行 tsc --noEmit、unit/contract tests，并把 generatedCode 与真实 runtime artifact 绑定。
P2 degraded 已被 sandbox/finish 拒绝，生产策略仍需显式化 sandbox 和 finish 现在会把 degradedAgents 视为不通过；但生产 runtime 仍有 fallback 行为，需要在 active 环境的策略、告警和 UI 上显式呈现。 为 active runtime 增加 degraded policy：fail-close / retry / emit fallback 三选一，并把 degraded decision 进入告警和 run detail。
P2 HITL 已持久化，但还不是 Directive 模型 新版本用 Postgres raw table 保存人工消息，解决了跨 worker 丢消息；但还缺 scope、author、status、consumedTurn 和 UI 审计。 升级为 HumanDirective 模型，支持 global/agent/event/test/deploy scope，并在 plan/trace 中标记 consume 结果。
P2 UI eval 有硬编码启发式 例如覆盖度用 agent 数量判断，和 ontology 的真实 expected coverage 不完全一致。 从 coverageGap / ontology event flow 派生 expected agent count 和 missing triggers。

08 · 相关研究与可落地启发

我把资料分成 Harness、Agent Loop、Multi-agent、代码生成评测、上下文管理和隔离执行六组。对我们最有用的不是“多加几个 agent”， 而是把评测、上下文、预算、trace 和安全边界工程化。

资料 关键观点 对 Agentic Operator 的建议
Harness Engineering · Martin Fowler Harness 是模型之外的全部工程：上下文、工具、权限、反馈、评测和环境。 继续把 v3 做成强 Harness；不要把成功率完全寄托于更大模型。
OpenAI Harness Engineering 人类设定目标与反馈，agent 执行；工程重点转为设计环境、反馈循环和可控执行面。 把 UI cockpit、SSE trace、HITL、finish gate 做成产品级交互，而不是 debug 附件。
ReAct 交错 reasoning trace 与 actions，提高可解释性和工具任务表现。 v3 已符合；下一步要把 trace 从“可看”升级为“可查询、可重放、可评测”。
Reflexion 用语言化反馈和反思记忆让 agent 从失败中学习，不改模型权重。 强化 FailureReflection：加 root-cause taxonomy、适用 domain、失效检测和检索排序。
MetaGPT 多 agent 若只是消息串联，会级联幻觉；SOP 与结构化产物能降低协作混乱。 若引入 subagent，必须给每个 subagent 明确 SOP、输入/输出 schema 和验收规则。
AutoGen Conversable agents 可以混合 LLM、人类和工具，以对话组织复杂任务。 适合 P2/P3 研究/规则拆解/critic，不适合默认把核心生成链路拆成多个自由对话 agent。
Anthropic Multi-agent Research 多 agent 擅长 breadth-first 并行研究，但 token 成本可达 chat 的 15 倍；不适合高度依赖链式任务。 Agent 工厂的核心链路高度依赖，默认保持单 brain；只在独立 research、tool audit、domain rule mining 使用 subagent。
AlphaCodium 代码生成需要测试驱动、多阶段、显式边界样例，而不是一次生成。 把 reverse-score harness 升为 P0：golden fixtures、branch tests、regression score、失败样例自动加入技能库。
CodeAct 可执行代码 action 让 agent 原生拥有控制流和数据流，复杂多工具任务可减少 action hop 并利用报错自我 debug。 只把少数复杂 Product Agent 升级到 CodeAct-style sandbox；简单事件 agent 继续用 spec executor。执行代码前必须有 out-of-process 隔离与 action audit。
DSPy 手写 prompt template 脆弱，应该把 LM pipeline 声明化并可优化。 把 design/review/refine prompt 抽成可版本化 signatures，未来用 evaluation set 自动优化。
CoALA 认知 agent 可拆成 memory、action space、decision loop 等模块。 把 v3 state 明确拆成 working memory、episodic trace、semantic skills、procedural tools。
Anthropic Context Engineering 长程 agent 的上下文会腐化；需要持续管理哪些 token 进入上下文。 为 compaction 建 loss audit：保留 hard constraints、last failure、coverage gap、sandbox fingerprint 等不可压缩状态。
Anthropic Long-running Harnesses 长任务需要 initializer、progress file、self-verify、干净环境与可恢复状态。 为每个 FactoryBrainRun 生成 machine-readable progress ledger，使 route 重启后可恢复。
ReSum / AgentFold / ACON 周期总结、主动折叠和优化压缩能缓解长 horizon agent 的上下文饱和。 用“可验证摘要 + 可检索原始 trace”替代一次性压缩；对摘要做 coverage/failure/fingerprint 校验。
AFlow 把 agentic workflow 表示成代码并自动搜索优化，可在成本更低模型上达到更好表现。 把 v3 工具调用序列作为 workflow 数据，未来离线搜索更优 build policy，而不是每次完全自由探索。
Firecracker microVM 提供强隔离和低开销，适合运行不可信或多租户 workload。 直接执行 AI 生成代码前，应引入 out-of-process / microVM 级 sandbox，而不是同进程 import。

09 · 推荐目标架构

我建议将 Agent 工厂目标架构定义为：一个单 Brain 主控、强 Harness 验收、可选 subagent 分工、可回放 trace、 可量化 reverse-score、统一合同、混合 runtime 的 Agent 生产线。

Lane A：Spec Executor

这是默认路线。承认 GeneratedAgentSpec 是正式部署 artifact，重点投入 contract、tool selection、 event graph、runtime decision eval、trace 和 golden tests。

适合：近期要稳定支持更多业务域、强调可控和快速上线。

Lane B：Behavior.compute

让 codegen 产物真正成为 makeOntologyAgent / Behavior.compute 的实现。 需要隔离编译、AST 审计、依赖白名单、类型检查和回归评测。

适合：需要工程师可读可改、可 PR review、可长期维护的 agent 代码资产。

Lane C：CodeAct Sandbox

让 agent 用可执行代码 action 组合多个工具、循环调试和复用中间变量。表达力最强，但必须 out-of-process， 并受网络、文件系统、依赖、secret 和 wall time 策略限制。

适合：少数多工具编排、动态数据分析、需要自我 debug 的复杂节点。

11 · 不建议做的事

不要默认多 agent 化核心链路

核心生成链路高度依赖，盲目加 planner/coder/reviewer 自由对话会放大 token 成本和级联错误。

不要同进程执行 AI 代码

当前不执行 AI 代码是安全的；一旦改成直接 import，就必须先解决隔离、依赖和权限边界。

不要把 terminal event 等同成功

finish 需要证明正确链路、分支和稳定性；看到 terminal 只是必要条件，不是充分条件。
