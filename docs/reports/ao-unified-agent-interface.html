人机共创,按本体分析出 agent 数量,
造出来部署到 Inngest 跑业务流

整个工厂是一套人机共创系统:人持续对话给意图;顶层 harness 大脑把"造 agent"拆成阶段性、可迭代的流水线,每阶段挑选 + 组合分形大脑能力 agent;所有 agent 共用一套统一接口和共享底座。关键:agent 数量不写死 —— 大脑读某域本体、分析出该域需要的 N 个 agent(招聘 v-1=6 / energy=17 / feikong=10),收敛成 N 个 Inngest function。造 agent 的两份料先备好:① action 定义在前(业务→本体);② 工具从开发文档生成入库(上传 / 爬网页 → AI 写 tool)。

01全景 · 整体技术架构

五个平面,自上而下:人 → 大脑 → 能力 agent → 统一底座 → Inngest 产物

从人说一句话,到本体所定的 N 个 function 跑在 Inngest 上,整条链分五层。上面三层是"怎么造"(人机共创 + 调度 + 干活),下面两层是"靠什么造 / 造出什么"(统一接口+数据底座 / 部署产物)。

"6"是怎么来的:产物 agent 数量不写死 —— 大脑读某域本体,把 actor=Agent 的动作分析出来,有几个就造几个。招聘 v-1=6、能源=17、费控=10。不同业务 = 不同本体 = 不同 N。
五平面全景。平面 2 新增 Doc-Fetcher / Tool-Smith;平面 3 底座新增"API 文档库"+ 工具库持久化。
逆向工程方法论(为什么有招聘 v-1 和 Agents-generation 两个域):要造并验证这套"任意本体 → agent"的系统,需要一个已知正确答案对照。
· 招聘 v-1 = 线上真实生产域,6 个手写 agent 在跑 = 答案键 / 黄金标准。
· Agents-generation = 工厂的开发测试域,喂同一套招聘本体让工厂自动生成。
· 对照:生成的 agent vs 招聘 v-1 的 6 个真 agent(签名/分支/工具)打分 → 分高 = 造得对。
验证通过后推广到没答案键的别的域(能源/费控)。

02阶段流水线 · 脊柱

分阶段跑,每阶段挑选+组合,失败就回环迭代

这是整套系统最重要的部分。顶层大脑把"造 agent"拆成阶段,每阶段只做两件事:挑选(用哪些能力 agent)+ 组合(怎么协作)。阶段之间能回环(验收不过 → 退回备料/建造)。人可在任一阶段打断、补料、改方向。

入口前提 —— action 先定义(你的工作流):业务需求 → 流程 → 在本体里定义好 action(及其事件/规则/DataObject)。工厂只读 action 生成 agent;业务变更先改 action,再触发重新生成。所以"理解/规划"之前,action 是人主导备好的料(料 1)。
6 阶段流水线 + 迭代回环 + 任一阶段人可介入 → 收敛成本体所定的 N 个 Inngest function。
阶段挑选+组合这一格能力 agent 自己派的 skill/sub-agent(例)产出
1 理解Researcher 们派 sub-agent 看别域相似本体域的世界模型
2 规划Orchestrator—N 槽建造计划(复用/生成)
3 备料Doc-Fetcher + Tool-SmithDoc-Fetcher 派 sub 爬/取 API 文档 → Tool-Smith 写 tool工具库齐活(契约+impl)
4 建造Agent-Builder 们派 skill「三级去重」「动态抓规则」织进 promptN 份 spec + AI 写的 .ts
5 验收Verifier 们派 sub 多视角对抗复核通过 / 打回(↩ 迭代)
6 部署大脑收口—本体所定的 N 个 Inngest function
关键:阶段流水线 = 把已有的 selection(挑)+ orchestrator(组合)+ meta-brain(流式调度)串成阶段、加回环。不是新机制,是把 select+compose 排成有阶段、能回退的过程。

03工具从文档生成 · Doc-Fetcher + Tool-Smith

上传 / 爬网页拿开发文档 → AI 写 tool → 入库 —— 就是和 Claude 对话让它写 tool

这是"备料"阶段的核心,也是把工具库从人手写变成AI 可填的那一跃。外部平台的 I/O(RoboHire 等)定义在工具库里;它们的 API 契约从开发文档来。文档有两条进料路径,Tool-Smith 把文档变成可用工具。

两条进料(上传 / Doc-Fetcher 爬取)→ Tool-Smith 写 tool → 校验 + dry-run → 人审 → 入库;全程对话式可改。

Doc-Fetcher · 取文档

用户给 URL / 上传,必要时爬网页(静态页 fetch+正文抽取;要 JS/登录的用无头浏览器)。专治"文档只在网页上"的平台(如 RoboHire 的网页 API 说明)。不自主乱爬 —— 只取用户授权的源。

Tool-Smith · 写 tool

读文档 → 抽 endpoint/参数/返回/auth → 写 ToolDescriptor(parameters/returns/impl/sideEffect/requiredEnv)+ impl 代码 → TS 校验 + dry-run。它是个 kind:builder 的分形大脑,能派 sub 去读多页文档。

安全检查点

上传/爬来的文档 = 数据,不是指令(防注入)。生成的工具人审后才入库,有写操作/副作用的尤其要人点头。爬网页要用户授权 URL。这是"自动执行"的护栏。

回答你的两个问题:① "要不要内部 agent 爬网页取文档" → 要,就是 Doc-Fetcher。② "能不能上传文档让 AI 写 tool 入库" → 能,就是 Tool-Smith,且全程对话式(像和 Claude 聊着把 tool 写出来)。两者合起来 = "备料"阶段的工具供给。

04分形大脑 · 每个 agent 也是大脑

大脑性是递归的:顶层是大脑,被它挑中的每个能力 agent 也是大脑

被挑中运行时,一个能力 agent 不是"死函数",它能动态生成 SKILL 或 sub-agent 辅助自己完成那一格的活。系统在每一层都"会思考"。

分形:顶层大脑 → 能力 agent(也是大脑)→ 各自派 skill / sub-agent 完成自己那一格。
为什么:把"会思考"下放到每个能力 agent,顶层大脑只管挑选+组合+阶段推进;每格"怎么干"由那个能力大脑临场决定。可扩展(加一类能力 agent 不动顶层)且更聪明。技术上递归 = ctx.spawn = 同一个 invoke(§06),带预算/深度上限。

05三类 agent · 为什么必须统一

同样叫 agent,生命周期天差地别 —— 各搞各接口 = N×M 接线地狱

能力 agent(内部辅助)

平面 2 那些:Researcher/Orchestrator/Doc-Fetcher/Tool-Smith/Agent-Builder/Verifier。按能力分、跨域复用(域作参数:同一个 Agent-Builder 吃招聘本体造招聘 agent、吃能源本体造能源 agent)。被函数式调用,产 artifact,临时。

会派子的 harness

上面每个能力 agent 运行时派 skill/sub-agent(§04)。"会派子"不是第三种实体,是一种能力位(spawns:true)—— 顶层大脑、能力 agent 都打开它。

产物 agent(Inngest)

平面 4 那些(招聘 v-1 是 6 个,数量由本体定):事件触发、持久、产业务事件。流水线的收敛物。绑本体事件签名、调工具库。

不统一的代价:大脑要用三套接口调度、注册表存三种形状、选择器写三套打分;加一类 agent 就改一圈。所以要在"调度/编排/观测"面统一 —— 见 §06。

06统一三件套 · AgentNode / invoke / spawn

统一 ≠ 都一样。统一 = 一个描述符 + 一个调用 + 一个递归

三类 agent 都被同一描述符装下、同一调用驱动、同一递归组合。kind 说它是什么、exec 说怎么跑它 —— 唯一的底座差异都收在 exec。

// ① 一个描述符,装下 能力 agent / 会派子的 / Inngest 产物
interface AgentNode {
  id; kind:"builder"|"harness"|"product"; capability
  input; output                 // product=事件签名; builder=入参/artifact schema
  tools:string[]; spawns:bool    // 能调的工具 / 会不会派子
  exec:                          // ★ 怎么跑它 —— 底座差异只在这
    | { substrate:"in-process", brainRef }   // 派一个 ReAct 子大脑
    | { substrate:"inngest", fnId }         // 发触发事件 + 观测 run
    | { substrate:"tool", toolRef }          // 直接调一个工具
  source:"preset"|"generated"|"human"; version; status; proven
}
// ② 一个调用,藏起底座    ③ 一个递归(= §04 分形)
runner.invoke(node,input,ctx): AsyncStream<AgentEvent>
ctx.spawn(childRef,input) === runner.invoke(...)  // 带父 ctx+预算+中断信号
已有 70%: agent-harness/types.ts · RegistryAgent 已带 id/capability/io/tools/source/proven,只差 kind / spawns / exec。扩成 AgentNode 即可。

07统一什么 · 故意不统一什么

最关键的工程判断:别把两个底座硬捏成一个

统一(一个接口)

✓ AgentNode 描述符 —— 注册/选择/编排一视同仁
✓ invoke —— 调用方不关心底座
✓ ctx.spawn 递归 —— 任何 agent 能派子
✓ AgentEvent 流 —— 一套 UI 渲染所有 agent

故意不统一(两个底座)

✗ 运行时 in-process ReAct ≠ Inngest 持久函数
✗ 触发 函数调用 ≠ 事件触发
✗ 生命周期 临时 ≠ 部署持久
✗ 产物 artifact ≠ 业务事件

判据一句话:"谁来调度、怎么编排、怎么观测" → 统一;"实际在哪跑、被什么触发、活多久" → 让 exec.substrate 去分。这条缝守住,加第四类 agent 也只是多一个 substrate 分支。

09架构调整与优化 · 深度思考

这套设计要求工厂在 5 个地方调整

A1 · 工具库:静态数组 → AI 可填的持久库

现在 RECRUITMENT_TOOLS 是硬编码数组。改成可持久化(DB 或 tools-library/<slug> 文件,仿 skills-library),让 Tool-Smith 写进去、可版本/回滚。这是"AI 造工具"的落点。

A2 · 底座加"API 文档库" + 文档进料

新增文档存储(上传 + Doc-Fetcher 爬取的开发文档),作为 Tool-Smith 的接地源。文档是工具侧的料,和业务侧的 action/本体并列。

A3 · action-first 作为硬前提

工厂只读 action 生成;业务变更先改 action 再重生成。建议在"理解"前加一个轻量action 对齐检查(本体里的 action 是否覆盖当前业务),人主导。料 1 备好才进流水线。

A4 · 安全/检查点策略(配合"自动执行")

爬取/上传内容 = 数据非指令(防注入);生成的工具/agent 人审后才入库/部署,写操作/destructive 尤其要人点头;爬网页要授权 URL。把"自动 AI 执行"关进护栏。

A5 · 把 select+compose 升成阶段机 + 版本化

meta-brain 之上加阶段状态机(理解→…→部署 + 回环);工具/agent 都版本化(AgentVersion 已有,工具补上),迭代可回退、可对照。

不用动的

对话持久化(刚做)、读本体喂全(刚做)、黄金标准对标(刚做)、注册/选择/编排 over RegistryAgent —— 这些都复用,扩 AgentNode 后直接吃三类 agent。
