该不该为「Agent 工厂」造一个 Code CLI Harness？

把现有 agent-factory-v2 / agent-factory-gen 代码读懂 + 针对 meta-agent 自生成系统做调研后的落地判断。研究覆盖 ADAS / AutoAgents / GPTSwarm / DSPy / Gödel / Voyager / CodeAct / CREATOR / Reflexion 与 Anthropic 工程实践。

9 agents · 4 读码 + 4 调研 + 1 综合 · ~60 万 token · 246 工具调用 · 结论已对硬盘逐项核验

① 结论：DESIGN，不要 CLI ② 硬盘真相核对（重要） ③ 为什么 code-CLI 是错的形状 ④ 五层架构（架在你已有 spine 上） ⑤ 用 6 个 agents 反向当 benchmark ⑥ 自建 / 借用 / 别建 三栏 ⑦ 上下文 + 记忆 + 草稿生命周期 ⑧ Claude-desktop 式 UI mockup ⑨ 参考项目 + 论文 ⑩ 风险 ⑪ 落地路线 P0–P5

01 结论

DESIGN 你自己的轻量 harness —— 不要套用 Claude Code / Codex 式 code-CLI

一个通用 code-CLI 存在的全部理由是「安全地编辑 + 运行任意代码、对着活的文件系统、由一个自治循环驱动」。而你工厂的产物是一份声明式 agent spec（从注册表绑定的 tools + LLM 写的 prompt + 事件 emit 图），由 graph-closure 静态校验 + 进程内 dryRun 模拟来验证 —— 根本不存在那个「任意代码」的攻击面，CLI 最重的那套机器（文件系统权限、命令白名单、多语言 sandbox）没有要守护的东西。唯一真正需要 CLI 级技术的地方是「执行生成出来的 agent 做评分」那一步 —— 而那里的答案是 microVM（e2b / Firecracker），不是 Docker，更不是 CLI。

✅ 该做的

把 Conductor（确定性编排 + 预算 + 账本 + 重放）建起来，包住一组 ReAct builders。这是缺失的核心。

♻️ 该借的

从 CLI 只搬 4 样真能迁移的：prompt 缓存、上下文压缩、per-builder ReAct 形状、trace/可观测（你已经有）。

⛔ 别碰的

7 档交互式权限分类器、文件系统写权限、命令白名单、原生 OS sandbox、把整个 CLI 当 spine。

03 为什么 code-CLI 是「错的形状」

这不是程度问题（"CLI 有点重"），而是结构问题：两者要解的根本是两件事。

🖥️ Code-CLI（Claude Code / Codex）

  • 目标：对着活文件系统，安全地编辑 + 运行任意代码
  • 循环：单个自治 ReAct loop，开放式探索
  • 不可信面：任意 shell / 任意源码 → 需要 7 档权限、命令白名单、OS sandbox
  • 产物：文件 diff / 命令执行

🏭 你的 Agent 工厂

  • 目标：在硬契约下编译一份声明式 spec（Inngest 函数 + 命名空间事件 + tool 注册表 + dual-write）
  • 循环：确定性多阶段 compile（comprehend→plan→generate→validate→smoke→repair）
  • 不可信面：一个 prompt 字符串 + 一份 tool 绑定列表 → graph-walk 就能校验
  • 产物：可直接被共享 executor 运行的 GeneratedAgentSpec

套 CLI = 引入一整套「沙箱化执行 / 文件系统权限」的机器，去守护一个不存在的攻击面。而且业界的常见轨迹是：用框架/CLI 快速起步（第 1 周）→ 撞上 token 与错误处理的墙（第 4–8 周）→ 把核心重写成一个 ~200 行的裸 harness 拿回控制权（第 12 周）。你现在套 CLI，等于主动回退到第 1 周。Inngest 那句话说得直白：「你的 agent 需要的是 harness，不是 framework」 —— 而 harness 正是你已经选的路。

04 五层架构 —— 全部架在你已有的 spine 上

L0 你已经有；L1–L4 是要建的，其中 L2 Conductor 是真正缺失的核心。

L0SPINE 事件总线 + 账本已有

Inngest 事件总线 · WriteThroughMiddleware → InngestEventArchive/RunArchive · agent-logger → AgentActivity/LogEvent · SSE 多路（/api/stream）。命名空间事件 ${domain}/EVENT 就是你真正的隔离边界（生成的 agent 不会误触发生产）。

L1SPEC / 搜索空间要建

一份共享的 GeneratedAgentSpec = AutoAgents 4-元组 {Prompt, Description, Toolset(从 lib/tools 注册表，现在是空的，先建), emit 图 + HITL 闸口 + 输出契约}。把 6 个 golden agent 序列化进同一格式。表达力测试 #1：如果这个 spec 表示不了全部 6 个，就是太窄了。

L2CONDUCTOR / 上下文权威缺失的核心

确定性编排器，它拥有上下文：comprehend(4 个并行 FacetAnalyst) → plan(Planner 发 N 份互不重叠的 brief，每份独占特定 emit) → generate(并行 builder：ToolSmith / SkillSmith / PromptWriter) → validate(graph-closure + BFS simulateChain 跑 dryRun 桩) → smoke → repair(MAX 3，Reflexion 式)。builder 只回传 ≤1.5k token 的类型化摘要 + 账本行号，绝不回传原始 ReAct 草稿 —— 这是防「上下文中毒」的关键。

L3LEDGER / 记忆要建

Prisma 加 FactoryBuildRun + FactoryBuildEvent + FactoryLlmCall，recordLlmCall 作为唯一 LLM 入口，强制 per-builder + 全局 token 预算。加 outcome/verdict + reflection 列 → 账本顺带变成情景记忆（Reflexion）。持久化的 DomainUnderstanding = 语义记忆；tool/skill 注册表 = 程序记忆。

L4DRAFT STORE + UI要建

扩展 draft-store.ts（它已有 draft/offline/archived 且只作用于 shell agents）。每次生成立刻存为 status=draft（og-* slug、域作用域、永不触碰 6 个真 agent）。validate→promote 闸口。UI：Claude-desktop 三栏，右侧栏吃 SSE BuildEvent 流。

05 用现有 6 个 agents 反向做 benchmark

关键认知（ADAS 框架）：这 6 个招聘 agent 同时是三样东西 —— 把它们当三样东西用：

① 种子档案

meta-agent 学习的起点（像 ADAS 用 CoT/Reflexion/Debate 当种子）

② 黄金 benchmark

每个候选都拿它打分（决策是否一致）

③ 表达力证明

能复现全部 6 个 = 搜索空间够宽

两阶段闭环

Phase 1 — DSPy 形状（去风险，不做自由代码生成）

  • 把 6 个真 agent（server/inngest/agents/*.ts）各序列化进 L1 spec
  • 抓它们已知好的 input→output 对当 golden case；切成 SEARCH 子集 与 HELD-OUT 子集 —— 不分开 = 过拟合这 6 个、学不到可迁移的东西（本领域 #1 失败模式，arXiv 2510.06711）
  • 写一个业务含义的 metric：候选是否在该 case 上得到同样的招聘决策（PASS / FAIL / HITL-park，同样的 emit 事件名 + 关键字段）—— 不是表面字符串匹配
  • 每个候选用 bootstrap 置信区间打分，不是单次 pass/fail（点估计太噪、排不了序）
  • DSPy 的 bootstrap 技巧：跑程序、只留通过 metric 的 trace → 反推出每个 agent 的 prompt/demo

Phase 2 — ADAS 形状（spec/代码搜索，跑在你的账本 spine 上）

  • 用 6 份反推出的 spec 作种子档案；循环：注入按 fitness 排序的档案 + tool 原语 + "最大化对黄金 benchmark 的 fitness" → meta-agent 吐候选 spec
  • 2 轮反思（含一份显式的「错误实现反模式清单」—— 大幅降 bug）→ sandbox / simulateChain 跑 → 出错最多 3 次自调试重试 → 在 SEARCH 子集打分 → 追加进档案
  • 最终在 HELD-OUT 子集报告；再做 迁移测试：把生成的 agent 指向第 7 个没见过的招聘任务（ADAS 验证过迁移有效）
  • GPTSwarm 收缩：6 个 agent 是固定流水线（简历→解析→规则校验→匹配→邀约），冻结图、先搜节点内部，比开放式代码搜索小得多
  • 留 Gödel 的「只在效用提升时接受」规则；拒绝它的内存自改（不可审计，毁掉你的留痕账本）
⚠️ 这正是你标记为「P2-5 sandbox 跑通」的工作 —— 它是 gating 依赖

在生成的 agent 真正执行（而不只是 simulateChain 桩派发）之前，benchmark 分数都是模拟的。别信桩派发给出的 1.0 分。 真要执行时用 e2b / 自建 Firecracker microVM —— 不是 Docker（共享内核，内核 CVE = 逃逸），不是 sandbox-exec（Apple 已弃用）。

06 自建 / 借用 / 别建

🔨 自建（你的核心）

  • 共享 GeneratedAgentSpec 搜索空间；把 6 个真 agent 序列化进去当种子 + 表达力测试
  • lib/tools 注册表（现在空）—— meta-agent 只组合已注册原语，不发明 tool 内部
  • Conductor（conductor/store/deploy/types 全缺）：确定性状态机 + 预算 + 重放
  • Prisma Factory 账本表 + recordLlmCall 单一预算入口（加 reflection 列）
  • 黄金 metric + bootstrap-CI 评分器（SEARCH/HELD-OUT 切分）—— 投资 harness/eval 先于 generator
  • assemblePrompt(role, understanding, brief, skills, reflections) 确定性投影函数 —— 这就是「prompt 按上下文动态生成」
  • 进程内验证沙箱：validateSpecs + simulateChain BFS over dryRun 桩
  • factory-v2 UI（page + components 都空）+ 右侧栏吃 SSE

♻️ 借用（从 CLI / Anthropic）

  • per-builder 的 ReAct 形状（借结构，不借 CLI）
  • Prompt 缓存稳定前缀（system + tool 目录 + 域 ontology 跨 builder 重发）→ ~90% 便宜的缓存读，最大即时成本胜利
  • 上下文压缩（handoff 式：留架构决策/未决问题/TODO，丢原始 tool dump）
  • 子 agent 委派 + 隔离上下文窗口 + ≤1–2k 摘要回传（Anthropic 多 agent 研究系统）→ 映射到 FacetAnalyst×4 与 per-brief builder
  • JIT 检索（CLAUDE.md 前置 + 按需 glob 混合）：给 builder ontology-fetch 工具，各拉自己 brief 涉及的对象
  • ADAS 的 meta-agent prompt 结构（档案 JSON + 最大化 fitness + 错误实现清单）+ 2 反思 + 3 重试
  • Voyager/CREATOR/Agent-Skills：code 为载荷 + description 嵌入为检索键；SKILL.md + frontmatter；创建→执行→纠错 = DRAFT→VALIDATE→PROMOTE

⛔ 别建

  • 7 档交互式权限分类器（守护工厂从不产出的任意 shell/code）
  • 文件系统写权限 / 命令白名单（没有活文件系统编辑面）
  • CLI 内的多语言代码沙箱、原生 OS 沙箱（sandbox-exec 已弃用；bubblewrap 跟 Docker + 网络白名单打架）
  • 把完整 code-CLI / Codex / Hermes 当 spine
  • MCP / 插件 / hooks 扩展机器（单一用途流水线，过早）
  • Docker 当代码执行沙箱（共享内核不够，用 microVM）
  • Gödel 式内存自改 / monkey-patch（不可审计，跟留痕冲突）
  • 跨 run 的 Voyager 向量 skill 注册表现在就建（高杠杆但需嵌入库，推迟到 P5）

07 上下文、记忆、草稿生命周期

所有来源都收敛到一句话：在长程多 agent 系统里，上下文/记忆控制是第一可靠性杠杆 —— agent 累积的是熵，不是智能。 无编排时失败率 41–86.7%。命名失败模式：上下文中毒 / 分心 / 混淆 / 冲突 / 目标漂移。让 Conductor 主动策展上下文，而不只是被动持久化。

情景记忆 EPISODIC

FactoryBuildRun/Event/LlmCall + reflection 列。Fixer 在 smoke 失败时写一句口头反思，注入下次 repair + 未来同域 Planner。这把只写账本变成会学习的记忆。

语义记忆 SEMANTIC

Integrator 产出的 DomainUnderstanding —— 持久化、跨 build 复用，作为单一真相源防止 facet 之间上下文冲突。

程序记忆 PROCEDURAL

tool 注册表 + Voyager 式 skill 库（P5）。SkillSmith 先按相似度检索已验证 skill，再决定是否新生成。

每次生成都进草稿（Voyager 门控 + Agent-Skills 打包 + CREATOR 修复 + 生产闭环去重）

DRAFT
立刻存草稿
每次生成 → status=draft + source run_id + intent。追加式、便宜、全留痕。draft 期不去重（去重会丢 provenance）。
VALIDATE
沙箱 + 批判
① 沙箱执行 capture stdout/err；② LLM-as-critic 判是否达意图 + description 是否可被检索。失败进有界 CREATOR 纠错环，仍 status=draft。
PROMOTE
提升 + 去重 + 限容
双层都过才 validated→promoted。提升时按 code/description 嵌入去重，LRU/用量限容。draft 永久留作历史，promoted 集保持严选。
REUSE
先检索再生成
任务时嵌入 intent、按相似度取 top-k promoted skill，miss 才合成。闭合 generate→validate→persist→reuse。

守则：自演化 tool 库会「误进化」 —— 严谨放在 PROMOTE 闸口（沙箱+批判+去重+限容），不放在 DRAFT 步。draft 宽松，promote 严格。

Agent Skills + 「Harness not Framework」(Inngest) — skill 打包格式(folder+frontmatter+渐进披露) + harness 决策的概念骨架。agent-skills · inngest harness

10 风险（按严重度）

风险说明 + 对策
① 进度误判 最大memory 说 80% 建好、硬盘是空骨架。按第 1 周排期；先 re-baseline 再估算。
② eval metric 承重噪声点估计 / 训练泄漏会让搜索乱走、过拟合 6 个。必须 bootstrap CI + held-out 切分。先建 harness/metric，再建 generator。
③ Planner 分工失败你观察到的真实 bug：Planner 出 4 个 vs 答案 6 个 → 悬空 emit。对策：plan 钉进账本、每 brief 独占 emit、每次 repair 重注入「6 个目标」。
④ sandbox = 唯一 CLI 级需求未真执行前分数是模拟的。要真执行用 e2b/Firecracker microVM，不是 Docker，不是 sandbox-exec。
⑤ 草稿洪水「存每次生成」不在 promote 时去重 + 限容会撑爆检索索引。严谨放 promote 闸口，draft 宽松永久。
⑥ 跨 builder 上下文中毒builder 互相继承原始草稿 → 错误中间结论变「事实」。强制隔离 + 类型化摘要回传；DomainUnderstanding 单一真相源。
⑦ 多 agent token 成本单 agent ~4×、多 agent ~15× token；花费解释 ~80% 质量方差。只在真并行处 fan out（4 facet、per-brief），smoke/repair 串行；recordLlmCall 强制预算。

11 落地路线 P0–P5

P0

Re-baseline + spine 落地

把 lib/agent-factory-v2/{types,store,deploy,conductor}.ts + lib/factory-auth.ts 至少 stub 到路由能编译；填 recruit-gen-v1 snapshot；Prisma 加 Factory 账本表；lib/tools 注册 5–10 个真原语。出口：路由能端到端流出一串（哪怕 trivial）BuildEvent。

P1

Spec + 黄金 benchmark（DSPy 形状，不做代码生成）

定义共享 spec；把 6 个真 agent 全序列化进去（表达力测试）；抓 golden case、SEARCH/HELD-OUT 切分；在 rule-check-verify 模式上（off-Inngest、Postgres 缓存）建决策一致 metric + bootstrap-CI 评分器。出口：仅凭行为复现全部 6 个、各带 CI。

P2

Conductor + 上下文权威

实现确定性 comprehend→plan→generate→validate→smoke→repair 状态机；recordLlmCall 单一预算入口；assemblePrompt 投影函数；builder 上下文隔离 + 摘要回传；Reflexion 写账本注入下次；plan 钉账本杀掉 4-vs-6 漂移。出口：重生成 ≥4/6 过 graph-closure + simulateChain、全程留痕。

P3

真沙箱执行（唯一 CLI 级需求）

smoke 从进程内 simulateChain 升级到在隔离 microVM（e2b 或自建 Firecracker —— 明确不是 Docker、不是 sandbox-exec）里真执行生成的 agent，配 2 反思 + 3 自调试。现在分数才是真的。跑第 7 个未见任务的迁移测试。出口：≥5/6 带真执行分 + 第 7 任务迁移通过。

P4

Draft store + Claude-desktop UI

扩展 draft-store：每次生成→立刻 draft；promote 闸 = 沙箱+批判+去重(嵌入)+限容。建 app/behavior/factory-v2/page.tsx + components/behavior/factory-v2/*，三栏右侧 inspector 渲染 SSE/账本流（子 agent 运行、思考/IO、生成卡片、校验闸 + 分数条）。去术语、i18n zh+en。出口：运维能看一次实时 build，看到每个 builder 的推理/IO，每个产出落成可审 DRAFT。

P5

跨 run 学习（推迟）

Voyager 式 skill 注册表：把接受的 SkillSpec 按 description 嵌入持久化进向量库；SkillSmith 生成前先检索 → 第二次生成同域时组合已验证 skill 而非重新发明。最高「越跑越聪明」杠杆，但需嵌入库，故意放最后。

一句话收尾。 别造 code-CLI —— 它守护的是你没有的攻击面。造一个 spec 编译 harness（Conductor + 账本 + 黄金 benchmark），架在你已有的 Inngest + 留痕 spine 上；唯一真需要 CLI 级技术的「执行生成代码做评分」用 microVM 解决。先建 harness 与 eval，再建 generator —— 把 6 个真 agent 当种子 + benchmark + 表达力证明。而且：先把 memory 与硬盘对齐，你在第 1 周，不是第 12 周。
