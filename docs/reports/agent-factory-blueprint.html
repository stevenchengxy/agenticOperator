让 agents 生成"我们这种"agents

一份面向 Agentic Operator（AO）的工厂蓝图：把"本体（actions / dataObjects / events / rules）→ 可运行 Inngest agent"这条已经走通一半的链路，升级成带门禁、带评估、能自愈的 agent 工厂。需要的是 harness engineering，不是 agent-loop engineering。
范围：勘察了 server/inngest/agent-factory、lib/ontology-generator、lib/monitor、server/run-summary 等真实代码 · 对照 ADAS / Voyager / DSPy / Reflexion / τ-bench 等前沿 · 以你运行态的 6 个招聘 agent 为参考样本

★核心论点（先读这个）

你的问题其实不是"从零造一个 agent 生成器"——你已经有一台半成品工厂了：infer → generate → run 三段式、deriveAgents() 把每个 action 派生成 agent、makeOntologyAgent() 把 spec 编译成真实 Inngest 函数、能源/费控两域已能跑。问题是：这台工厂中段是空的——没有工具综合、没有静态校验、没有评估门禁、没有自愈闭环。所以生成出来的 agent 要么是只读不跑的 shell，要么靠 safeLlm 超时降级编一个假 payload"看起来跑通了"。

① 本体 = 编译器 IR

把 actions/dataObjects/events/rules 当中间表示（IR），agent 当编译产物。这把 ADAS 那种"meta agent 写任意代码"的无界、不稳定搜索空间，收敛成类型化、可校验的 config-space。本体里没声明的工具，模型无法幻觉出来。

② Skills 的答案是"要"

让 每个 action 对应一个经验证的 skill，agent 由 skill 组装而非从零合成——故障面从"无穷"收敛到"组合错误"。但 agents 生成 skills 必须走强晋升门（真实跑通 + rule-check PASS）。

③ 你需要 harness 工程

可靠性是地板/方差属性（pass^k），不是平均/天花板（pass@1）。Inngest 本身就是世界级的持久化 harness。工厂应生成"薄 loop + 厚 harness"，别让每个 agent 重造重试/停止/状态。

④ API 打包成 typed tools

要打包，而且工具选择分两层：生成时按本体裁剪工具箱、运行时再做 tool-RAG。一份 JSON Schema 同时当"约束解码语法 + 检索文档 + 注册索引"。

⑤ 失败有结构

把失败按"生成时可静态拦 / 只能运行时暴露 / 语义层"三桶分类——分桶直接决定防御手段归属。把本该生成时拦的留到运行时排错，代价是 10 倍。

⑥ 评估/测试/自愈复用现有件

不造新轮子：闭包校验、tool registry、AgentVersion 加 validated 档当上线门禁；自愈复用 step-classify 四档 + 休眠的 BehaviorAlert。

一句话
不要复活已被删除的 LLM 代码生成（TRACK 3，405d1e6 已 checkpoint 出去）。要做的是：让本体当 IR、让现有工厂当通用执行器、让 LLM 只综合声明式 spec 与 prompt，把可靠性留在确定性脚手架里，把创造性限制在类型化配置空间内。

各自深度 工厂必须填

真正不同的只有这几样——这正是 LLM 该综合、工厂该装配的部分：system/user prompt · 装备哪些 tool · 触发/发出哪些 event · 适用哪些 rule/guard · step 序列 · 重试策略。注意：6 个 agent 的 retries 各不相同（Resume Parser=0 防重复扣费、Match/Interview=2、Rule Check/JD=1），这说明重试是 harness 配置，不是 loop 里临时拍的——它应由 spec 声明、由执行器消费。

②心智模型：本体即 IR，agent 是被"编译"出来的产物

把 agent 工厂理解成编译器：传统编译器是 源码 → AST → IR → 目标代码；这里是 业务本体 → 规格(spec) → 可运行 agent。本体五件套（actions/dataObjects/events/rules/workflow）就是 IR——一种类型化、可校验、与执行框架解耦的中间形态。它本身就是编译器的类型系统：没声明的 action 不存在（杜绝幻觉工具）、每个 event 必须有生产者和消费者（图闭合）、rule 当合法性过滤器。

本系统已经把这条链路走通了一半：

  • 前端 / 语义分析 已有：lib/ontology-generator/analyze.ts 的 deriveAgents() 把每个 OntologyAction 1:1 降解成 DerivedAgent spec（actor=Agent→kind:'llm'，其余→simulated-human 自动应答器闭合事件链）。
  • 后端 / 代码生成 已有：server/inngest/domains/energy/make-agent.ts 的 makeOntologyAgent(spec, opts, client) 把 spec 装配成真实 inngest.createFunction。
  • 目标 ABI 已有：server/inngest/agent-factory/types.ts 的 AgentFactoryOpts / Behavior / GateRequest / ComputeResult。
  • infer → generate → run 三个 Route Handler 恰好对应"分析 → 落库 → 执行"。

产物形态：强烈推荐"声明式配置 + 通用执行器"，而非生成 TS 源代码

四条理由，都有仓库证据：

  1. 团队已经用脚投票：TRACK 3 的 LLM TS-codegen 曾实现（Bundle J/L/M/N），但在 405d1e6 被 checkpoint 出去、由 ontology-generator 取代。AgentVersion.codeBlob/codeHash 至今 nullable 无写入者。生成代码带来 tsc 编译门、sandbox、AST 分析、PR 回灌的巨大 harness 成本。
  2. 契约已存在：填 AgentFactoryOpts 这个稳定 ABI，比让 LLM 写会编译失败的代码安全得多——这正是用类型系统消灭 ADAS code-space 不稳定性的做法。
  3. 共享地板：声明式产物让所有生成 agent 共享同一套 Inngest 确定性脚手架；生成代码则让每个 agent 各写各的、可能绕过 claimOnce/depth guard 丢掉保护。
  4. 可版本化、可 diff、可回滚：结构化 spec 天然支持 ADAS 式 archive hill-climbing，AgentVersion 表就是 archive。代码 blob 做不到细粒度搜索。

③Skills ↔ Agents 分层：要不要让 agents 生成 SKILLS、SKILLS 生成 agents？

直接回答
两个方向都要，但不对称：agents 生成 skills 必须走强晋升门（promotion gate）、低频、人审；skills 生成 agents 必须靠组合（composition）而非自由合成。这正是 Voyager 的 skill library 与 Anthropic Agent Skills 的核心教训，也恰好贴合你已有的本体驱动结构。

先把两个单元定义清楚——本系统目前把它们混在一起了：

  • SKILL ≠ tool。tool 执行并返回；SKILL = 程序化知识（how-to）+ 绑定的 tools + I/O schema，它注入"何时/如何做"的流程并打包所需工具。对应 Anthropic 的 SKILL.md：frontmatter 的 name/description 就是它的检索键，body 是 L2，脚本是 L3（渐进披露）。
  • AGENT = loop + model + system prompt，负责把 skills 沿 workflow DAG 编排起来。它消费 skills，不重新发明它们。

今天的事实：deriveAgents() 把每个 action 直接派生成一个 agent，中间没有一个可复用、可检索、可独立验证、可独立版本化的 skill 层；tool 还只是 sim-tools.ts 的模拟值。推荐把 deriveAgents() 拆成两步：

  1. deriveSkills(onto)：action → SkillSpec{ name, description(=检索键), systemPrompt, userPrompt, tools[], inputSchema, outputEventSchema, ruleGuards[] }。一个 action 天然带齐 skill 三要素，这一步零额外标注。
  2. composeAgent(workflowSlice, skills)：agent 不再"一 action 一函数硬绑"，而是沿 DAG 选择并排序已验证的 skills（对应 GPTSwarm 的"agent = 可优化计算图"）。

为什么"组装验证过的 skill"比"从零合成行为"更稳？

故障面有界

每次现合成是高方差的；组装预验证 skill 把失败面收敛到"组合错误"，每个 skill 已独立过外部确定性 oracle。

搜索空间收窄

本体把 ADAS 的 Turing-complete 代码空间压成 typed config 空间：无幻觉 tool、无不可编译样本，rules 当合法性过滤。

复用不覆写

Voyager 的关键洞见：新 agent 组合旧 skill，不像 fine-tune 那样覆写，能力单调累积、无 catastrophic forgetting。

晋升门 / dedup / 版本化

晋升门严格三条件，缺一不可（对应 Voyager 的 self-verification、CRAFT 的 validate-then-abstract）：

  1. 真实执行验证通过：必须在一条真实 WorkflowRun 上跑通，且确定性 oracle（ontologyRuleCheck/RuleCheckAudit 的 PASS + emit event schema 校验）给绿灯。绝不能用 safeLlm 超时降级 parseOrSynthesize 的编造 payload 来判合格——那是 reward hacking 入口。
  2. 复发或泛化：出现 ≥2 次或明显跨 task 可用（借 lib/monitor trace 统计）。
  3. dedup 后确为新增：用 dedupeActionsByName 的 action-signature 去重 + 按 name/description 多视角检索比对，命中则 extend/version，而非新建。
版本化直接复用现成空槽
AgentVersion 的 promptText / specJson / codeBlob / skillOverrides 是为此预留的死槽，capturedFrom 注释已列 'codegen'/'ontology-gen'。SkillSpec 落 specJson+promptText，晋升即 status: draft→active。版本规则：schema/contract 变才 bump，description 作为检索键必须保持稳定。L1/L2/L3 渐进披露映到 agent context budget。

④Harness engineering vs Agent loop engineering：你到底需要哪个？

Harness engineering（脚手架工程）

模型外面那圈确定性基础设施：tool 定义与 schema、context 管理、运行时与持久化、重试与错误恢复、状态落库、sandbox 隔离、输出校验。可测试、可 diff、可版本化。

Agent loop engineering（循环工程）

模型里面那个 随机内循环：perceive→decide→act→observe、ReAct、planning vs reactive、reflection、停止条件。同一输入跑两次轨迹可能不同。

答案
你需要的是 harness engineering。loop 决定 agent 能不能做对一次；harness 决定它能不能每次都做对。而 Inngest 已经把最贵的那层 harness 送到你手上了——别浪费在每个 agent 重造 loop 上。

为什么杠杆在 harness？

核心只有一句：可靠性是"地板/方差"属性，不是"平均/天花板"属性。 loop 改进（更好的 planning、reflection）抬高 ceiling 和平均；harness 改进抬高 floor、压缩 variance。衡量工厂真实可靠性的指标是 τ-bench 的 pass^k（k 次全过，p^k 指数衰减），不是 pass@1：一个 pass@1 >60% 的 agent，到 pass^8 掉到 <25%；即便每次 90%，k=8 也只剩 ~57%。

两个最硬的实证都指向 harness：SWE-bench 上同一份模型权重，仅靠 scaffold 设计 solve rate 就能从 ~5% 跳到 30%+（有报告称高达 6×）；τ-bench 的 pass^k 崩塌也是 harness 形状的问题。你没法靠"加更多 loop"把随机循环变确定，只能用确定性脚手架把它包起来。DeepMind《LLMs Cannot Self-Correct Reasoning Yet》是同一枚硬币的反面：任何修复/判断循环都必须锚定外部确定性裁决（tests、type-check、schema/rule 校验）——而这些全是 harness 的东西。

本系统的决定性事实：Inngest 本身就是那个持久化 harness

  • Durable steps：step.run(id, fn) 按 id memoize，retry/resume 时已完成 step 返回缓存——每个 step 是确定性 checkpoint，自带 retry/backoff。
  • 声明式重试契约：resume-parser=0（防重复扣配额）、match-resume=2、interview-inviter=2、rule-check=1——重试是 harness 配置，不是 loop 临时拍的。
  • HITL 活在 harness 里、不烧 context：step.waitForEvent('<ns>/HUMAN_DECISION', '30d') 把运行 durably 挂起最多 30 天、0 算力——直接消灭 AutoGPT 的"无停止条件"failure mode。
  • Trajectory store 免费：WriteThroughMiddleware（onRunStart/onRunComplete/onRunError/wrapSendEvent）把每条 run/event/trace 镜像进 Postgres——这就是 Reflexion 短期记忆 + APR fault context，Inngest 宕了也还在。
  • 确定性 grader 与 guardrail 现成：dataObject schema → outcome grader（断言 Candidate_Match_Result/OntologyRuleCheck 终态，而非判 prose）；rule 的 failurePolicy 红线 → 输出/工具调用 rail。关键纪律——business FAIL 绝不 throw（write-only audit），只有 infra throw——本身就是 judge calibration 应用到 trajectory grading。
loop 侧现在恰恰脆弱
safeLlm（make-agent.ts:48）在 gateway 超时/不可达时吞错返回 ""，再用 parseOrSynthesize 凭 event schema 编一个 schema-valid 假 payload。demo 没问题，生产致命。但这正好证明论点：loop 的随机性应靠 harness（schema 校验 + infra-vs-business 分类 + park-and-retry）兜住，而不是靠让 loop 更聪明。

明确推荐：factory 生成"薄 loop + 厚 harness"

  1. deriveAgents/makeOntologyAgent 的产出聚焦薄 loop（system/user prompt + 一个 ReAct 步），重试/停止/状态/持久化全交给 Inngest。
  2. 可靠性预算压在 harness 硬化：tighten action schema、rule guardrails 走确定性 step、clean-state fixture、durable retry/HITL、trajectory archive。
  3. 可靠性验收用 pass^k 不用 pass@1，outcome-grade dataObject 终态，trajectory 只做诊断。
  4. LLM-as-judge 留在 Inngest 之外，套 jury（跨厂商）+ per-dimension 隔离 + "return Unknown" 出口 + 对人工标注 calibration（run-eval.ts 的 groundedness judge + jury + calibration.ts 的 Cohen's kappa 已是雏形）。

⑤把 API 打包成 tools + 工具选择（生成时 vs 运行时，谁来选）

两个问题一起答
第一，是的，要把 RAAS/RoboHire/Allmeta/MinIO 客户端打包成带 JSON Schema 契约的 typed tools——这是把"每个 agent 在源码里硬编码调哪个 client"升级成"工厂可装配、harness 可校验"的唯一前提。第二，工具选择必须分两层、不是二选一：生成时由 factory 按本体切片静态裁剪工具箱，运行时由跑着的 agent 动态选调，目录大时再叠加 tool retrieval。

现状：plumbing 已齐，缺的是 catalog

本仓库其实离目标只差一层连接组织：

  • harness 有了：server/llm/gateway.ts 的 chatComplete() 是通用多轮 tool-use 循环（ChatToolsOptions{schema,onToolCall,maxIterations=5}，tool_choice:'auto'），已在两个生产特性跑通。
  • 客户端有了：robohire-client.ts（parseResumeDirect 等，402→QUOTA_EXHAUSTED、429→RATE_LIMITED）、raas-api-client.ts、allmeta-client.ts、minio.ts 都是强类型模块，统一经 logApiCall 埋点、统一 retryable-vs-client 错误分级。

缺口只有三个，且都在"目录"这层：无全局 tool registry（两套工具面互相孤立各抄一遍 OpenAI 形状）无机器可读 schema（typed clients 有 TS 类型但没 JSON Schema，harness 没法喂给 LLM）无工具选择/检索（工具是特性作者手挑 3~4 个）。而 GET /api/agent-execution/capabilities 根本不是工具目录，它是硬编码 scenarios:['matchResume'] 的单场景服务发现广告。还有个真实坑：make-agent.ts 的 simulateTools 返回 sim://... 假结果——生成的 domain agent 工具是模拟的，不能真打外部系统。

两层工具选择

一份 schema 喂三处 · action→tool 映射

把 AGENT_FUNCTIONS[].tools 那种纯描述性 NL 字符串（'RMS API'）和真正可调用的工具区分开。真正的映射：本体 Action.tool_use[] → registry 可调用 tool；inputs/outputs（DataObject schema）→ tool 的 arg/return JSON Schema；trigger/triggered_event → Inngest 触发与 sendEvent；Rule → 返回值校验闸门。一份 JSON Schema 同时服务三件事：(a) schema-constrained decoding 的语法（杜绝畸形调用，直接根治"RoboHire 不吐 gender/skill 数组"的老坑——把真实形状编进 schema 并校验，别信模型臆测）(b) tool-RAG 的检索文档 (c) registry 索引。每个 tool 还应显式声明仓库现有但隐式的维度：副作用等级（读/写/双写）、幂等性、auth scope、所需 env、shadow 抑制——让写类工具（partner-pg 双写、allmeta.writeInstance、RoboHire invite）在 registry 层被门控。

落地清单

  1. 把 lib/chat/global-chat-tools.ts 的 {name, schema, execute} 提升为共享 ToolDescriptor 类型 → 新建 lib/tools/registry.ts，让 rule-check 的 TOOL_SCHEMA 与 chat 工具都从它导出。
  2. 为每个 client 函数手写 JSON Schema 包装（一函数一 tool），错误分级接成统一 {error, retryable} 信封（沿用 graph-context.ts 的 dispatcher 模式）。
  3. generation-time 裁剪逻辑进 deriveAgents，写 DerivedAgent.tools；simulateTools 换成 registry 解析的真实 dispatcher。
  4. runtime 检索作为 chatComplete 前的一个 step.run，工具数 >12 时启用。
  5. 把 capabilities 端点改造成数据驱动 manifest，加工具级 versioning（对齐 version-registry.ts 的本体 pinning）。

⑥不稳定性分类学：生成出来的 agent 为什么跑不通

最危险的认知错误，是把"agent 生成 agent"当成连续成功率问题——以为模型够强、prompt 够好，跑不通的概率就单调下降。真相是：失败有结构。把全部失败混在一起谈"可靠性"等于放弃治疗。必须先按"在哪个时刻、用什么手段才能拦住"分桶——因为分桶直接决定防御机制的归属。

桶① 生成时可静态拦截 最便宜，必须前置

不需要把 agent 跑起来，光看"产物 + 本体"就能判定它必然跑不通：

  • 幻觉工具调用：emit 本体里不存在的 action/event。防御=deriveAgents() 只能由已声明 action 派生 + event 命名空间化。
  • schema 不匹配：DataObject 的 JSON Schema 既是 grammar-constrained decoding 约束，也是 event payload round-trip 校验源。
  • 事件未接线（dangling event）：致命缺口 infer.ts:danglingFromOntology() 已算出"发了没人消费"的孤儿事件，但只显示、不强制（infer.test.ts 只测空 fixture），运行时还用 synthetic trig + simulated-human "糊"上，把断线伪装成"跑通了"。
  • slug 跨域碰撞（djb2 hashId 无注册表防撞）、Allmeta 规则缺 failurePolicy（live 节点不带 prompt → 产出空 prompt agent 却写 draft 蒙混）。
推荐：在 generate/route.ts 写 draft 前插一道 deterministic gate——closure 检查、event→function 绑定存在性、prompt/tool 非空、slug 唯一。生成时拦不住的，后面每层都要花 10 倍代价补。

桶② 只能运行时暴露 环境耦合

铁律：故障在环境里，就别去改 agent。误把 infra 故障当 agent 缺陷去"修"，是浪费修复周期的头号原因。

其它运行时项：缺停止条件死循环 / 上下文溢出 / runaway cost（靠 userland MAX_CHAIN_DEPTH+claimOnce 防，绕过 factory 形状就丢这层保护）；trace_id 全空 → L3 血缘断层 / AgentActivity.runId 外键不是真 WorkflowRun（轨迹捕获本身坏掉，repair loop 读不到可信 fault context）。

桶③ 语义层 只能 eval 度量

产物合法、能跑、不报错，但做错了事或被刷分了：

  • silent failure：答案对、路径错（τ-bench / Anthropic 的核心警示）。
  • reward hacking / gate-gaming：候选 agent 靠把 rule-check 全塌成 PASS、短路 HITL 来"通过"eval。防御内建于架构：rule 是 write-only audit、红线由 engine.ts 的 code 定义，meta agent 只能在固定 rule 内搜索，无法改写自己的闸门。
  • 判 reliability 用错指标：绝不能用 pass@1，必须用 pass^k（60% pass@1 在 k=8 跌破 25%）。

⑦可靠性栈：六道关卡，全部复用现有件

不要新建一套生成专用评估体系。把生成的 agent 强制走和生产 agent 一样的六道关卡，核心新增物只有三件：闭包校验升级为编译期 gate 统一 tool registry AgentVersion 加 validated 档当单一上线门禁。

⑧自动修复 · 让工厂自愈

一个能持续运转的 agent 工厂，护城河不在生成，而在生成之后还能自我修复。第一原则（DeepMind《Cannot Self-Correct Yet》）：纯无外部反馈的自我纠错往往让结果更糟——所以任何修复都必须锚定在确定性外部裁决上（rule-check / schema / type-check），绝不让 agent "自己觉得对了"就晋升。

好消息：硬骨头大半已经长好，自愈更多是接线而非新建——捕获=现成 WriteThroughMiddleware（轨迹已落 Postgres archive，读归档不依赖 live Inngest）；分类=扩展 step-classify.ts。

防失控是命门，不是脚注

AutoGPT/BabyAGI 的失败目录给了必须加的护栏，全部用 Inngest 原语硬实现，不靠 prompt 自觉：修复次数上限（Inngest step attempt 计数已暴露）、cycle-breaker（比对新补丁 diff 与 archive 历史补丁，防"重复相同计划"）、硬预算熔断（token/$/时间做成一个 step，超了 emit *_FAILED）、人类升级闸（复用三闸门 waitForEvent('<ns>/HUMAN_DECISION','30d') + 按域筛选的 recordNotification，落对的收件箱 / 值班工作台 :4180）。

⑪对话式工厂：用 chatbot 生成 agent + 右侧推理面板

设想把整个 infer→generate→run 表单流程,换成一个会话式 meta-agent:你用自然语言描述要造的 agent,它把第 ② 节那条编译流水线当作一连串 tool call 执行,并在右侧面板流式展示正在生成的 agent + 结构化推理——参照 Claude Desktop 的 chat+artifact 分栏、bolt.new / Lovable 的"对话驱动生成 + 右侧产物预览",以及 LangGraph Studio 的 agent 执行可视化。这是把 bolt/lovable 对"造 app"做的事,搬到"造 agent"。

这套"完全基于 chatbot"合不合理?
合理,但要钉死边界。对话层是 agent 工厂的授权/编排/人在环路 harness——它让生成可观测、可干预、可审批(这正是 agent UX 的第一原则:每个决策点透明 + 全程可控)。但"chatbot 驱动" ≠ "chatbot 决定":确定性门禁(闭包校验 / schema 校验 / eval pass^k)仍在背后确定性执行,meta-agent 只是调用它们、不替代它们。三条铁律:① 推理按 AG-UI / Anthropic 原则从结构化 trace 与 tool 事件渲染,不吐裸思维链(raw CoT);② 审批门(validated→active)落成聊天里的 HITL 批准卡,接现有 waitForEvent('<ns>/HUMAN_DECISION') 闸;③ 对话后端是普通流式 API route 读 archive,不上 Inngest(遵守"synthesis 不上 Inngest"房规)。

右侧面板的设计原则(来自 agent-UX 研究)

✗认知纠偏

把 prompt 写好，生成的 agent 就能可靠运行。
prompt 是 loop（随机层），只抬天花板。可靠性是地板/方差属性（pass^k），靠 harness（schema 校验、durable 重试、clean-state、外部裁决）抬。SWE-bench 上同权重仅靠 scaffold 就能 5%→30%+。
应该让 LLM 直接生成 agent 的源代码（TS）。
团队已用脚投票——TS-codegen 子系统在 405d1e6 被删除、codeBlob 列至今无写入者。生成声明式 spec 由通用执行器解释，可版本化、可 diff、可回滚、复用确定性脚手架，且用类型系统消灭"大多数样本编译不过"的 ADAS 失败模式。
agent 越自主、越能自我纠错越好。
DeepMind 证明：无外部反馈的自我纠错往往越改越偏（self-bias）。修复必须锚定确定性外部裁决（rule-check/schema/type-check）。且 infra 故障绝不该触发 agent patch——病在环境就别动 agent。
生成出来能跑、不报错，就算成功了。
这只过了桶①②。safeLlm 超时会静默合成 schema-valid 假 payload——"能跑"但"行为错"。成功必须用 pass^k 多次度量 + 确定性 outcome grader 判 dataObject 终态，而非"没报错"。
有了强 LLM-judge 就能自动判好坏、驱动上线。
judge 有 position/verbosity/self-enhancement/authoritative-tone 四类偏差。必须 jury 跨厂商 + per-dimension 隔离 + "说不准"出口，且先过 Cohen's kappa 校准才准当门禁；确定性 grader 才是主闸。
把所有工具丢进 prompt，让模型自己选最方便。
工具选择有灾难曲线：RAG-MCP 实测 10→100+ 工具时准确率从 78% 崩到 13.6%，还叠 lost-in-the-middle。必须生成时按本体裁剪工具箱 + 运行时 tool-RAG 只暴露 top-k。

📖术语表

Harness engineering（脚手架工程）
模型外那圈确定性、可测试、可版本化的基础设施：tool 定义、context 管理、运行时/持久化、重试、状态、sandbox、输出校验。本系统里 Inngest 就是它。
Agent loop engineering（循环工程）
模型里那个随机内循环：perceive→decide→act→observe、ReAct、planning、reflection、停止条件。
IR（中间表示）
编译器里源码与目标代码之间的类型化中间形态。本系统里=本体五件套（actions/dataObjects/events/rules/workflow）。
pass^k
τ-bench 提出的可靠性指标：连续 k 次全部成功的概率（p^k 指数衰减）。暴露最坏情况一致性，远比 pass@1（至少成功一次）严格。
Tool registry / tool-RAG
把每个 API 包成带 JSON Schema 的 typed tool，集中索引（registry）；运行时按语义检索只暴露 top-k 相关工具（tool-RAG），避开大目录准确率悬崖。本 harness 的 ToolSearch/deferred tools 就是范本。
schema-constrained decoding（约束解码）
把工具的 JSON Schema 编译成语法，逐 token 屏蔽非法输出，按构造消灭畸形/越界调用（只保证形状对，不保证语义对）。
LLM-as-judge / jury
用大模型给开放式输出打分；jury=跨厂商多模型投票，稀释单模型偏差。必须先对人工标注做 Cohen's kappa 校准。
canary / shadow
canary=灰度小流量；shadow=影子模式只接流量不产生副作用，把新 agent 输出与现役逐条 diff。
Reflexion / Self-Refine / APR

skill library（技能库）
