02 · 智能体卡片

每个 agent = 一张可处置的卡片

卡片把「黑箱生成」变成「逐个过目」。每张卡片有完整生命周期与三个动作:

✓ 采纳

认可这个 agent。它进入待部署集;只有全部采纳 + 沙箱全跑通,才能 finish 落 Fleet 草稿。

↻ 重想

让 AI 重新设计这一个(可附一句提示,如「工具少了落库」)。触发 refine/重新 design,只重做这张卡,不动别的。

✎ 直接改码

你自己改 prompt / 代码 / schema。改完走同一套校验(TS 编译 + import/事件接地),并标记为「人工编辑」。

卡片状态机

03 · 决策点

AI 拿不准时,主动给你几个方案 +「其他」

与其偷偷拍板一个可能错的值(如匹配阈值、归属策略、是否需要面试),不如把不确定性显式抛给你。新增一个大脑工具 ask_user:它产出问题 + 2-3 个带理由的选项 + 一个「其他」输入框,然后挂起等你选,你选完(或填 other)再继续。

触发时机由 AI 自己判断:阈值/分档/策略这类「没有唯一正确答案、且影响业务」的点才问;能从本体或规则确定的(如事件名)绝不问。问太多会烦,所以 ask_user 的 prompt 里明确「只在真有业务歧义时用」。

04 · 打断与重路由

你中途说一句,Harness 自己判断回到哪个节点重跑

底部介入条随时可用。你打一句话(「把 createJD 改成监听 INTERVIEW_INVITED」),Harness 在 turn 边界收到后,不是从头再来,而是判断这句话影响哪个节点,只回到那个节点重执行,再用确定性的 verify_chain + 行为门重新验证整条链。

已经有的地基:我上一轮做的人在环路邮箱(turn 边界注入人类消息 + 进状态摘要)就是这条的底层。这次新增的是「把打断分类成『重做哪个节点』」的智能 + UI 上的可视化反馈(「↩ 已回到 createJD 重新执行」)。

05 · 要补的技术细节(事件 + 接口 + 状态)

让上面三套交互真的能跑的底层契约

新增 / 扩展的流式事件(大脑 → UI)

事件含义UI 渲染
agent.proposed一个 agent 设计好,等你确认(不再自动往下)展开的「待确认」卡片 + 采纳/重想/改码
agent.state卡片状态变更(采纳/重想中/沙箱中/已采纳)卡片徽章 + 状态机推进
choiceAI 不确定 → 问题 + 选项[] + allow_other内联决策卡,挂起等选
route.back打断后判定重路由到某节点「↩ 已回到 X 重执行」横幅 + 该卡回到待确认

新增的入站接口(UI → 大脑,走同一邮箱机制)

接口载荷大脑侧
POST …/agent-action{runId, agent, action: accept｜regenerate｜edit, hint?, code?}转成该 agent 的待办,drive 状态机
POST …/choice{runId, choiceId, optionId｜otherText}解挂 ask_user,返回选择
POST …/inject (已有){runId, text}打断 → 重路由分类

新增的大脑工具

  • ask_user(question, options[], allow_other) — 抛出不确定决策,挂起等人选。只在真有业务歧义时用。
  • propose_agent 取代「设计完自动 codegen」 —— 改成设计完先 propose,等人采纳再 codegen(每节点一道人工闸,可配置「自动采纳」跳过)。
  • 打断分类内建在主循环:收到人类消息 → 让大脑判断「这是改某节点 / 改全局计划 / 只是提示」→ 走最小重路由。
状态来源单一可信:每个 agent 的卡片状态 = ctx.specs[i] + 一个 cardState 字段;采纳/重想/编辑/沙箱结果都写这里,UI 只是它的投影。这样刷新、压缩、回放都不丢卡片状态。
06 · 回扣宏观架构

这些交互,正是元编排的「人工决策节点」

前端这三套交互不是孤立功能,它们是宏观蓝图里人在环路与元编排重规划的具体落点 —— 把抽象的「人机协作」变成可点的按钮:

卡片采纳闸

= 元编排在每个节点上的人工 approval gate。对应「Build-vs-Reuse」之后的「人是否认可这个节点」。

决策卡 (ask_user)

= 元编排遇到自己没把握的分叉时,把决策权上交给人,而不是赌一个。

打断重路由

= 元编排的重规划入口:人给新约束 → 重新点将/重做受影响节点。这正是「返回哪个节点重执行」。

顺带补的两个架构技术点

  • 智能体注册表 schema(P1 地基):{ id, name, source: generated｜handwritten, domain, capability, triggerEvents[], emitEvents[], inputSchema, outputSchema, codeRef, version, status, sandboxProof }。选择 Harness 按 triggerEvents/emitEvents + capability 检索;卡片采纳后写入。
  • 选择 Harness 的匹配:先确定性(事件签名 + 域精确/超集匹配)→ 再 LLM 语义排序候选 → 给出「复用 X(置信度)/ 没有合适的,建议生成」。决策权仍在元编排(可被你用决策卡覆盖)。
07 · 落地顺序

前端重设计,增量四步

F1
卡片化 + 状态机:把现有 agent 区改成卡片,接 agent.proposed/state + POST agent-action。采纳/重想/改码三键先跑通(沙箱仍自动)。
F2
决策卡:加 ask_user 工具 + choice 事件 + POST choice + 内联选项 UI(含 other)。
F3
打断重路由:在已有 inject 邮箱上加「分类→最小重路由」+ route.back 可视化。
F4
每节点人工闸 + 决策点历史 tab + 可配置「自动采纳」开关(从全手动到全自动连续可调)。
不破坏现有自治:默认仍可一键全自动(自动采纳 + 不问),交互层是可选的方向盘——想接管时随时接管,不想管时它自己跑完。这就是你要的「自治 × 人机协作」连续光谱。

一句话总括

把工厂从「AI 自己跑、你只能看」,升级成「AI 主跑、你随时能接管」的共创画布:每个 agent 一张可采纳/重想/改码的卡片,AI 拿不准就给你几个方案+其他,你一句话打断它就自己判断回哪个节点重跑——自治不减,但方向盘随时在你手边。
