01 结论速览

直接回答你的核心疑问——"App 在 Inngest 面板上消失了，是不是后端挂了？"

结论 A 后端现在没有挂，而且不是在反复崩溃。

当前 next-server (v16.2.4)（PID 88657）自 11:56 起稳定运行，GET /api/inngest 7ms 返回 200。系统里那一堆 next dev 进程是 被 Ctrl-Z 挂起（状态 T = stopped）、不是崩溃——崩溃会消失、不会留下进程。说明后端是被你手动挂起/反复重启的，而非自己 crash-loop。

结论 B "App 消失" ≠ "后端挂了"，二者在 Inngest 面板上长得一模一样——这正是你分不清的原因。

Inngest dev server 的 "Apps" 列表不是持久状态，而是一个"此刻能不能同步上 SDK"的实时视图。只要 dev server 某一次回调 http://host.docker.internal:3002/api/inngest 失败（超时 / 拒绝 / 慢），它就把 App 从面板移除；下次成功又自己冒出来。所以 App 消失可能是后端真死了，也可能只是那一刻同步超时（后端好好的）。光看面板无法区分——需要第 ⑤ 节的方法。

结论 C 没有任何进程守护——这是"不稳定"最致命的一环。

整个后端跑在一个前台终端里（ttys011，状态 S+），没有 pm2 / launchd / systemd。一旦后端真的崩溃、终端被关、或笔记本合盖休眠，没有任何东西会把它拉起来——这时 App 才是"真·长期消失"。本质上：你把一套开发模式（next dev + inngest dev）当成了部署在跑，而且是在一台会休眠、被十几个其它服务挤占的共享笔记本上。

03 核心机制：App 为什么会"消失"

理解这一条，后面所有根因都串起来了。

Inngest dev server 在 dev 模式下用 pull / 周期回调来维护 App 列表：它拿着容器启动参数 -u http://host.docker.internal:3002/api/inngest，反复去回调你后端的这个 URL来确认 App 还活着、抓取最新的函数清单。

环境拓扑（当前 = Docker 版 Inngest，跨了一道 Docker 网络边界） ┌─────────────────────── macOS 主机 (会休眠的共享笔记本) ───────────────────────┐ │ │ │ next dev :3002 ◀───── ② dev server 周期回调 /api/inngest ──┐ │ │ (前台终端, 无守护) │ │ │ │ 每次回调都会跑 getPausedSlugs() ──▶ Postgres :5433 │ │ │ │ │ │ │ └──── ① 发事件/注册 ─────────────────────────────┐ │ │ │ ▼ │ │ │ ┌──── Docker Desktop VM (8GB) ──────┴──────┐ │ │ │ ao-inngest :8288 (dev server) │ │ │ │ -u host.docker.internal:3002 ────────┘ │ │ └──────────────────────────────────────────────┘ │ ▲ │ │ 归档器 ──── 每30s 拉 events/runs ──┘ (这条也观测到 6 次 5s 超时) │ └──────────────────────────────────────────────────────────────────────────────┘

关键事实："Apps" 列表不持久化。只要 ② 这次回调失败（超时 / 连接拒绝 / 500 / 太慢），dev server 立刻把该 App 标记为不可达并从面板移除；下次回调成功再重新出现。于是：

"App 消失"  ⟺  dev server 在那一刻够不到 host.docker.internal:3002/api/inngest

而"够不到"有一大堆彼此独立的原因，且每一个在本机都已观测到迹象——这就是它"有时候挂、有时候好"的本质：不是单一 bug，而是多条脆弱链路叠加。逐条列在下一节。

04 根因清单（按可能性 / 证据强度排序）

  1. 无进程守护 + 后端被反复挂起/重启 已证实
    后端跑在前台终端，没有 pm2/launchd。每次你 Ctrl-Z 挂起、关终端、或 npm run dev 重启，后端就够不到 → App 立刻消失。崩溃后也无人重启。
    证据：多个 next dev 进程处于 T（stopped/挂起）状态，时间戳横跨周四 17:00、周五 11:00、今天 11:23 / 11:25 / 11:28；当前进程链 S+ 挂在 ttys011；launchctl/pm2 均无对应条目。
  2. /api/inngest 的存活被耦合到了 Postgres 架构脆弱点
    app/api/inngest/route.ts 在每一次 dev server 回调里都先 await getPausedSlugs()（一次 DB 查询）才返回函数清单。Postgres 抖一下 / 慢一下 → 这个回调超时 → App 被判不可达 → 掉线。本该只是"列出函数"的探活，被绑上了一次数据库往返。
    证据：route.ts 的 pickHandler() 每个 GET/POST/PUT 都调 getPausedSlugs()；bootOnce() 在首个请求时还会跑 env 检查 + 启动 raas-bridge + Neo4j sync。
  3. Inngest dev server（Docker）间歇性无响应 已观测
    归档器每 30s 拉一次 Inngest，有 6 次直接 5s 超时。容器本身只吃 76MB、没 OOM——所以超时来自 Docker Desktop VM 在主机高负载下的网络转发(vpnkit)/vCPU 调度 stall。这一刻 dev server 对所有人（归档器 + 它自己的回调循环）都变慢，App 也会同步掉线。
    证据：logs/inngest-archiver.log 出现 6 行 tick FAILED: Inngest dev server timeout after 5000ms，分散在不同时段（前后都是正常 tick，说明是瞬时 stall 后自愈，非崩溃）。
  4. 把 dev 模式当部署 + 跨 Docker 网络边界 与已知经验冲突
    此前记录的经验是 "AO 的 Inngest 要用 native inngest-cli，不要 Docker"。但现在 Inngest 又跑在 Docker 里——因为 scripts/dev-bootstrap.mjs 每次 npm run dev 都优先 docker compose up 重建容器，把 native 选择覆盖掉了。Docker 版多了一道 host.docker.internal + VM 端口转发，正是上一条超时的来源；native CLI 直连 localhost 没有这层。
    证据：端口 8288/8289/5433 的 LISTEN 属主是 com.docker（PID 94968）；docker-compose.inngest.yml 用 -u host.docker.internal:3002；dev-bootstrap.mjs 注释明写 "prefer Docker"。
  5. 启动顺序：Inngest 先起、后端后起 时间窗口
    dev-bootstrap 先把 Inngest 容器拉起，&& 之后才 next dev。所以容器启动后有一段时间后端还没起来，dev server 的 -u 回调必然失败 → 这段窗口里 App 是缺失/报错的，直到后端起来并被成功回调。今早 11:23–11:56 的反复重启期间，App 会跟着每次重启一并闪掉。
    证据：容器 Started 03:25:29Z(≈11:25 本地)，而当前后端起于 11:56:45；其间多个被挂起的 next 进程印证了这段重启churn。
  6. 笔记本休眠 高度怀疑
    合盖/休眠会把后端、Docker、归档器一起冻住。唤醒后 Docker 容器恢复，但 App 要等 dev server 重新成功回调后端才会回来——这中间面板上就是"消失"。
    证据：归档器自周四 17:00 常驻至今（≈3 天）按 30s 应有 ~8000+ tick，但日志只有 3276 行 → 中间有大段停顿，符合笔记本夜间休眠。
  7. 主机资源争抢拖慢回调 放大因素
    同机并行跑 12+ 个 allmeta next dev + raas backend + Apifox + Cursor，load avg ~4。AO 的 next dev 被 CPU 饿着时，/api/inngest 回应变慢，更容易在 dev server 的同步超时阈值内掉线。这条单独不致命，但会把上面每一条的概率往上推。
    证据：ps 列出大量 allmeta/raas node 进程；load average 3.56/4.41/4.77；Docker VM 仅 8GB。

06 修复建议（按优先级，本次未执行）

按你的要求只诊断、不动代码。下面是建议清单，确认后我可以逐条实施。

  • P0 · 给后端加进程守护 + 自动重启
    这是把"偶发消失"变"自愈"的最高杠杆。最轻量：用 pm2 托管 npm run dev（崩溃自动拉起、开机自启、脱离终端）；或写个 until node …; do sleep 2; done 的 keepalive，配合 caffeinate -dimsu 防休眠。当前裸前台终端 = 任何一次崩溃/关窗/合盖都是永久下线。
  • P0 · 解耦 /api/inngest 探活与 Postgres
    给 getPausedSlugs() 加短 TTL 缓存 + 超时兜底（拿不到就按"全部启用"返回，别让回调卡在 DB 上）。让 dev server 的同步回调几乎纯内存、毫秒级返回，Postgres 抖动不再能把 App 拽下线。对应根因 ②。
  • P1 · Inngest 回到 native inngest-cli（与已记录经验一致）
    去掉 Docker VM 那道网络/转发边界（根因 ③/④ 的来源）。具体做法：把 dev-bootstrap.mjs 的 "prefer Docker" 改成探测到 native inngest-cli 在跑就不 docker compose up，并常驻 inngest-cli dev --host 0.0.0.0。若坚持 Docker，至少让 bootstrap 不要每次重建容器、并修启动顺序（先后端后 Inngest，或让 dev server 起来后重试）。
  • P1 · 加一条"App 掉线"主动告警
    不要靠人盯面板。归档器已经在 30s 轮询——给它加一句：连续 N 次同步不到 agentic-operator-main（或 connected:false）就打日志/发通知。这样"消失"被主动捕获、且自带时间戳，便于回溯到底是哪一类。
  • P2 · 如要长期稳定，别用 dev 模式当部署
    长远看，next dev（HMR/按需重编译）+ inngest dev（明确的开发工具、状态易失）不适合当"部署"。稳定形态是 next build && next start（无重编译）+ 独占/不休眠的机器 + 一个真正常驻的 Inngest。至少先把 AO 从这台挤了 12+ 服务的共享笔记本上挪开，或给它 caffeinate + 降低同机并发。
  • P2 · 给归档器日志加时间戳
    当前 [archive] tick ok… 没有时间戳，导致没法把 6 次超时对到具体时刻、也看不出休眠停顿的确切区间。加上 ISO 时间戳后，这份报告里的多数"高度怀疑"就能升级成"已证实"。

AO 监控页去拉 Inngest 数据时，拿回来的是一个 HTML 网页（以 <!DOCTYPE html> 开头），不是 JSON。代码对这个响应直接调 res.json() 去解析，第一个字符 < 就让 JSON 解析器爆掉 —— 这就是 Unexpected token '<' 的字面来源。AO 随后落到降级分支，显示"事件引擎不可达 · 缓存数据"横幅。

结论 C 根因：AO 服务端解析出的 Inngest 读取地址，指向了一个"会返回 HTML 的源"，而不是真正的 Inngest :8288 JSON API。

我把这个报错逐字复现出来了（见第 ⑩ 节）：当读取 URL 落到 AO 自己的应用（:3002 / 部署域名 / 反向代理）时，POST <那个地址>/v0/gql 返回的正是 Next.js 的 <!DOCTYPE html><html lang="zh">… 页面 —— 连 lang="zh" 都和你的报错对得上。极可能是部署机上 INNGEST_BASE_URL 配错（指到了应用 / 域名 / 漏了 :8288 端口），或在远程主机上保持了默认 localhost:8288（那台机上没有 Inngest）。

11 为什么"Inngest 能跑、AO 却不显示"能同时成立

因为"执行"和"显示"走的是两条完全独立的链路——不同 env、不同方向、不同端点。

① 执行方向（这条是通的 → agent 真在跑）
Inngest ──回调──▶ AO
用 INNGEST_SERVE_HOST = host.docker.internal:3002/api/inngest
→ 函数被调起来，run 正常产生
② 显示方向（这条断了 → 监控读不到）
AO ──读 runs/functions──▶ Inngest
用 INNGEST_BASE_URL + /v0/gql
→ URL 错 / 回 HTML → 解析爆 → 横幅

两条链路毫无关系，所以"① 通 + ② 断"完全可能 —— 这恰好就是你看到的现象。放大问题的几处代码 / 配置：

  1. 监控的 live 读取硬依赖 dev-server-only 的 /v0/gql
    inngest-admin-client.ts 顶部注释写"prod 应指向 Inngest Cloud 的 REST API"，但代码里根本没有 Cloud 那条路 —— listFunctions / listRecentRuns / getRunHistory 全打 /v0/gql。所以监控只在"读取 URL = 一台真正的 Inngest dev server、版本对、返回 JSON"时才工作。
  2. listFunctions 永远走 live，无归档兜底
    inngest-source.ts:86 把 listFunctions 直接 = live 版。所以"函数列表 / agent 健康"面板永远暴露在这个失败下，即使 runs 有归档保护。
  3. 归档只在"窗口里有行"时兜底
    auto 模式下 archive.listRecentRuns() 返回 0 行（空闲时段 / 窗口内没 run）就落到 live。所以哪怕归档表里有历史（本机 runs=62/events=97），一个没有近期 run 的时间窗也会触发 live gql() → 暴露在 URL 故障下。
  4. 与问题一联动 → "有时候"才出现
    问题一里 Inngest（Docker）会偶发 stall / 重启。那些瞬间 live gql() 可能拿到非 JSON（代理 502 页 / 启动中的 SPA HTML），叠加 gql() 无守卫 → 横幅间歇闪现，与你说的"有时候不稳定"吻合。

14 能不能直接在 AO 总览里配置？（你的问题）

答案 不能。总览里那个"同步新 App"按钮修不了这个问题——它管的是另一个方向，而且那个方向已经通了。

总览里的"同步新 App"实际做什么而 unreachable 需要改的是
POST /api/inngest-admin/sync-app {url}
→ ${INNGEST_BASE_URL}/fn/register
把 AO 的 serve 地址注册给 Inngest（执行方向，Inngest→AO）。
生产里这条已经成功（截图：23 functions 在）。再点也是冗余。		 读取方向用的 INNGEST_BASE_URL。
它在 inngest-admin-client.ts 里是 const BASE = getInngestUrl()，模块加载时一次性从服务端 env 读取。
浏览器 UI 改不了服务端 env；UI 里也没有设置读取 URL 的输入框。

三个独立理由叠加，决定了"总览配置"这条路走不通：

  1. 方向不对
    "同步新 App" = 注册 AO→Inngest（执行）；unreachable = AO→Inngest 读取。前者已通、后者才是病灶，两者不是一回事。
  2. 读取 URL 是 boot-time 常量
    const BASE = getInngestUrl() 在模块加载时定死；要变更必须改 env + 重启 AO 进程。UI 点按钮不会重读 env。
  3. 连按钮本身都依赖那个坏 URL
    sync 按钮也走 ${getInngestUrl()}/fn/register。好在它 strip 了结尾斜杠，所以按钮可能"能用"——但它修的不是读取路径，点了也不会让总览变绿。

（若真想"在 UI 里改 Inngest 地址并立即生效"，那需要改代码：把 getInngestUrl() 从读 env 改成读运行时设置（DB/配置表）、并让 BASE 不再是 const。但对当前这个 bug 来说没必要——根因只是一个多余的斜杠。）

15 真正的修法（改配置，不改代码）

  • P0 · 去掉 INNGEST_BASE_URL 结尾的 / 然后重启 AO
    在那台生产机的 AO 部署 env 里：
    INNGEST_BASE_URL=http://raas-inngest:8288  （删掉结尾斜杠）
    顺手把 NEXT_PUBLIC_INNGEST_URL 也设成同样无斜杠的值。改完重启 AO 容器（env 在启动时读）。然后回到总览的「系统配置」弹窗看：状态应翻成健康、已注册函数 → 23。
  • P1 · 顺带确认 raas-inngest 这个服务名从 ao-main 容器能解析
    既然之前能收到 HTML，说明 raas-inngest:8288 是可达的（不是 DNS 死）——所以去斜杠极可能直接修好。万一去斜杠后变成连接错误（而非 HTML），那就是 ao-main 与 raas-inngest 不在同一 Docker network / 服务名不对，再核对 compose 的 networks + service 名。
  • P2 · （可选，需改代码）让读取 client 也 strip 结尾斜杠
    在 getInngestUrl() 里 .replace(/\/+$/, '')，或 inngest-admin-client.ts 的 BASE 处理一次。一行就根除这一整类"多打个斜杠就全挂"的脆弱，和 sync-app 的既有写法对齐。问题二建议里的 gql() 加 res.ok/content-type 守卫一并做更好。
方法论：本报告遵循 systematic-debugging（先定根因再谈修复）。未对任何代码或运行中的服务做改动，仅执行只读探测（ps / lsof / docker inspect / curl / GraphQL 查询 / 源码追踪）。
问题一局限：归档器日志无时间戳，故"笔记本休眠""资源争抢"两条标注为"高度怀疑"而非"已证实"——见建议 P2（加时间戳）即可升级确认。
问题二：报错链路已从前端→路由→client 逐行追到代码，并用 curl 把 Unexpected token '<' 逐字复现。
问题三：两张生产截图坐实了根因 = INNGEST_BASE_URL=http://raas-inngest:8288/ 结尾多一个斜杠 → 双斜杠 //v0/gql → Inngest 回 dashboard 网页。已实测双斜杠确实返回 SPA HTML。修法是去斜杠 + 重启 AO（改配置，非改代码）；总览的"同步新 App"按钮修不了（属另一方向，且已同步成功）。
