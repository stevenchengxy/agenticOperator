Agentic Operator · AllmetaOntology · Neo4j

运行时实例写入 Neo4j 后，如何按 Links Schema 创建实例 Links

本文档说明 AO 的 functions / Inngest agents 在运行过程中把实例数据写入 AllmetaOntology / Neo4j 后， 如何基于已经生成好的 AllmetaOntology links schema 自动创建业务实例之间的关系边。

0. 结论先行

实例数据不能只写成一批孤立节点。AO 每次写入 Candidate、Resume、 Application、Job_Requisition、Candidate_Match_Result、 Communication_Log、Interview_Record 等实例后，需要额外执行一层 Instance Link Generation：读取 AllmetaOntology 已生成的 links schema，找出当前实例 payload 中的外键字段，然后调用 Allmeta 的实例级 link API 在 Neo4j 中创建实例关系。

推荐做法：AO 不在每个 function 里手写关系；新增一个集中式 LinkPlanner + LinkWriter。 所有函数只负责声明“我成功写入了哪些实例”，由 LinkPlanner 按 schema 自动推导关系。
补充要求：规则检查审计本身也要成为可持久化的多页审计书，而不是只保存一个结论字段。 它需要拆成封面、输入快照、规则筛选、逐规则判断、证据、Prompt、响应、实例与回放等页面， 并在 Neo4j 中和候选人、简历、岗位、规则、匹配结果建立 instance links。
关键边界：/api/v1/ontology/links 是 schema/meta link，不应该被 AO 当成业务实例 link 使用。 实例与实例之间的边应走 /api/v1/ontology/instance-links?domain=...，或者由 Allmeta 提供一个等价的语义实例 link endpoint。

1. 核心概念

概念 含义 例子
DataObject Schema AllmetaOntology 中定义某类业务对象的结构、主键、字段。 Candidate.primary_key = candidate_id
Instance Node 运行时产生并写入 Neo4j 的真实业务数据节点。 (:Resume {resume_id: "R001", candidate_id: "C001"})
Links Schema AllmetaOntology 根据对象定义、外键、描述、业务语义生成的“类型级关系定义”。 Candidate --targets--> Resume，证据字段 Resume.candidate_id
Instance Link 两个真实实例节点之间的 Neo4j relationship。 (Candidate C001)-[:TARGETS]->(Resume R001)
FK Evidence links schema 中用于判断实例关系的外键证据。 evidence.source = "fk"，field = "candidate_id"

本方案的核心不是让 AO “猜关系”，而是让 AO 只执行 schema 已经声明过、并且能从实例 payload 中找到外键证据的关系。 这样关系生成是可解释、可回放、可回补的。

2. 目标运行流程

1. Function 运行 resume parser、JD creator、rule check、match resume、interview inviter 等。
2. 生成实例 payload 包含业务主键和外键字段，例如 candidate_id。
3. 写实例节点 调用 /instances/{label} 写入 Neo4j。
4. 收集写入结果 返回 label、pk、payload、traceId、runId。
5. LinkPlanner 读取 links schema，根据 FK 推导应创建的 links。
6. LinkWriter 调用 /instance-links 创建实例关系。
7. 观测与回补 记录成功、跳过、失败、pending，支持后续 replay。

运行时写入结果的最小结构

每个 Allmeta instance writer 写完节点后，应给 LinkPlanner 一个统一的结构：

{
  "domain": "RAAS-v1",
  "label": "Resume",
  "pkField": "resume_id",
  "pk": "R001",
  "payload": {
    "resume_id": "R001",
    "candidate_id": "C001",
    "job_requisition_id": "JR001"
  },
  "traceId": "trace_xxx",
  "runId": "inngest_run_xxx",
  "writer": "resume-parser-agent"
}

这样 functions 不需要知道具体有哪些 links，也不需要手写 Candidate -> Resume。 它只要把“成功写入了什么实例”交给 LinkPlanner。

3. 如何解释 AllmetaOntology Links Schema

3.1 RAAS links schema 的实际形状

当前 RAAS links schema 文件是带元信息的对象，核心数组在 links[] 中：

{
  "metadata": {
    "domain": "RAAS-v1",
    "version": "..."
  },
  "links": [
    {
      "id": "object/Object/Candidate/targets/Object/Resume",
      "kind": "object-fk",
      "from": { "type": "Object", "id": "Candidate" },
      "to": { "type": "Object", "id": "Resume" },
      "action": "targets",
      "inverse_action": "...",
      "cardinality": "1:N",
      "semanticRelationship": {
        "zh": "...",
        "en": "..."
      },
      "evidence": [
        {
          "source": "fk",
          "artifact": { "type": "Object", "id": "Resume" },
          "field": "candidate_id",
          "reason": "Resume.candidate_id references Candidate."
        }
      ]
    }
  ]
}

3.2 运行时只使用哪些 links

Link kind 是否用于实例 links 原因
object-fk 使用 明确表示对象之间由外键建立业务实例关系，是运行时创建 links 的主来源。
object-composition 可使用 如果 schema 中有可验证 FK evidence，也可以生成实例关系。
action-* / rule-* / event-* / workflow-* 默认不使用 这些是 ontology 元数据关系，不是运行时业务实例之间的关系。

3.3 只信 FK evidence，不信纯描述

links schema 中有些关系来自 description、semanticRelationship 或模型推理。运行时自动建边时，应该只处理满足以下条件的 link：

  • kind 是 object-fk 或带明确 FK 的 object-composition。
  • from.id 和 to.id 都是 Object / DataObject。
  • evidence[] 中至少有一条 source = "fk"，且有 artifact.id 和 field。
  • 当前实例 payload 中存在该 field，并且值不是空字符串、空数组或 null。
这条规则很重要：它防止 AO 根据“语义上可能有关”创建不可验证关系。运行时自动化只做证据充分的事情。

4. LinkPlanner 推导算法

4.1 输入

InstanceWriteResult[] writtenInstances
LinkSchema[] schemaLinks
PrimaryKeyMap pkByLabel

4.2 单条 schema link 的判断逻辑

对每条 schema link，先提取：

fromLabel = link.from.id
toLabel   = link.to.id
action    = link.action
fk        = first evidence where evidence.source == "fk"
fkOwner   = fk.artifact.id
fkField   = fk.field

然后按 FK 在哪一侧来判断实例边方向：

情况 含义 生成实例 link
fkOwner == toLabel 外键字段在 to 端实例上，指向 from 端实例。 from.pk = payload[fkField]，to.pk = current.pk
fkOwner == fromLabel 外键字段在 from 端实例上，指向 to 端实例。 from.pk = current.pk，to.pk = payload[fkField]
fkOwner 不是两端之一 schema 证据不够直接，或者 link 通过第三方对象表达。 跳过，记录 skip_reason = unsupported_fk_owner

4.3 伪代码

for each writtenInstance in writtenInstances:
  for each schemaLink in schemaLinks:
    if schemaLink.kind not in ["object-fk", "object-composition"]:
      continue

    fk = findFkEvidence(schemaLink)
    if not fk:
      continue

    fromLabel = schemaLink.from.id
    toLabel = schemaLink.to.id
    fkOwner = fk.artifact.id
    fkField = fk.field

    if writtenInstance.label != fkOwner:
      continue

    fkValue = writtenInstance.payload[fkField]
    if isEmpty(fkValue):
      skip("missing_fk_value")
      continue

    for each targetPk in normalizeToArray(fkValue):
      if fkOwner == toLabel:
        planLink(
          relation = relationType(schemaLink.action),
          from = { label: fromLabel, pk: targetPk },
          to   = { label: toLabel, pk: writtenInstance.pk },
          schema = schemaLink
        )

      if fkOwner == fromLabel:
        planLink(
          relation = relationType(schemaLink.action),
          from = { label: fromLabel, pk: writtenInstance.pk },
          to   = { label: toLabel, pk: targetPk },
          schema = schemaLink
        )

4.4 relationType 生成规则

links schema 中的 action 通常是小写 snake_case，例如 records_for。 Neo4j relationship type 和当前 Allmeta instance-links handler 要求大写类型名， 因此需要一个稳定转换： 

relationType(action):
  trim action
  replace all non [A-Za-z0-9_] with "_"
  collapse repeated "_"
  uppercase

examples:
  "targets"                  => "TARGETS"
  "evaluates_fit"            => "EVALUATES_FIT"
  "records_process_for"      => "RECORDS_PROCESS_FOR"
  "archives_interaction_log" => "ARCHIVES_INTERACTION_LOG"
上线前必须和 AllmetaOntology 对齐：schema 侧用于校验的 link_name / name / relation 到底存小写 action，还是大写 relationship type。 推荐统一为：schema 保留小写 action，同时写入大写 link_name； instance link API 用大写 linkName 创建 Neo4j relationship。

5. API 调用契约

5.1 实例节点写入

AO 运行时先写实例节点：

POST /api/v1/ontology/instances/Resume?domain=RAAS-v1
Authorization: Bearer <ONTOLOGY_API_TOKEN>
Content-Type: application/json

{
  "resume_id": "R001",
  "candidate_id": "C001",
  "job_requisition_id": "JR001",
  "source": "ao-runtime"
}

5.2 实例关系写入

实例写入成功后，再按计划创建 instance link：

POST /api/v1/ontology/instance-links?domain=RAAS-v1
Authorization: Bearer <ONTOLOGY_API_TOKEN>
Content-Type: application/json

{
  "linkName": "TARGETS",
  "from": { "label": "Candidate", "pk": "C001" },
  "to":   { "label": "Resume",    "pk": "R001" },
  "properties": {
    "schemaLinkId": "object/Object/Candidate/targets/Object/Resume",
    "schemaAction": "targets",
    "schemaKind": "object-fk",
    "fkField": "candidate_id",
    "source": "ao-runtime",
    "traceId": "trace_xxx",
    "runId": "inngest_run_xxx",
    "linkKey": "RAAS-v1|Candidate|C001|TARGETS|Resume|R001"
  }
}

5.3 不要混用 schema links API

Endpoint 用途 AO 运行时是否应该调用
/api/v1/ontology/links 创建或读取 ontology schema 层面的关系，例如 DataObject 与 DataObject 的 link 定义。 不用于业务实例边
/api/v1/ontology/instance-links 创建真实业务实例节点之间的关系。 推荐使用
/api/v1/ontology/instance-semantic-links 按 schema 语义自动推导 relationship type 的实例关系 API。 可作为 Allmeta 侧演进方向，但需确认它支持真实实例节点，而不是 mock instance 节点。

7. 规则检查审计也要是“多页书”，并且持久化

规则检查审计不能只是一条 RuleCheckAudit 结果记录，也不能只依赖前端临时拼装。 它应该被建模成一本可分页、可追溯、可回放的 Audit Book： 封面记录本次审计的结论和索引，内页记录输入快照、规则选择过程、逐规则判定、证据、Prompt、LLM 原始响应、实例写入与 links 结果。

推荐原则：Postgres 负责审计列表、筛选、分页和快速读取；Allmeta / Neo4j 负责把审计书与 Candidate、Resume、 Job_Requisition、Rule、Candidate_Match_Result 等实例连接成图。两边都要有稳定 ID 和 hash，保证可重放与可校验。

7.1 审计书的数据结构

对象 粒度 主键建议 用途
RuleCheckAuditBook 一本审计书 / 一次规则检查运行 audit_id 封面和索引：候选人、简历、岗位、结论、runId、traceId、模型、耗时、规则数量。
RuleCheckAuditPage 一页审计内容 page_id = audit_id::page_type::ordinal 多页展示和分页持久化：输入页、规则选择页、判断页、证据页、Prompt 页、响应页、实例页。
RuleCheckFlag 一条规则判定 flag_id = audit_id::rule_id 记录每条规则的 applicable、result、severity、evidence、next_action。
RuleEvidenceBlock 一段证据 evidence_id = flag_id::n 保存引用的简历片段、JD 字段、图查询结果、人工反馈或 LLM reasoning 摘要。
PromptSnapshot 一次模型输入 prompt_id = audit_id::prompt::n 保存 system prompt、user prompt、prompt hash、token 估算、截断策略。
ResponseSnapshot 一次模型输出 response_id = audit_id::response::n 保存 LLM raw text、解析后的 JSON、parse_error、模型 request id。

7.2 多页书的页面清单

前端看到的是“多页审计书”，后端持久化的是 page records：

page_type 页面名称 持久化内容
cover 封面 结论、失败原因、candidate / resume / JR anchor、agent、stage、run、trace。
input_snapshot 输入快照 parsed resume、job requisition、runtime_context、hsm_feedback。
rule_selection 规则筛选 纳入 / 排除的规则、tier、reason、规则库总数、筛选后数量。
rule_judgment 规则判断 逐规则判定表：PASS / FAIL / REVIEW / NOT_TRIGGERED / INSUFFICIENT_INFO。
evidence 证据页 简历证据、岗位证据、图查询证据、人工反馈证据，按 rule_id 分组。
prompt Prompt 页 system prompt、user prompt、prompt hash、prompt source、schema version。
response 模型响应页 LLM raw text、解析 JSON、parse error、token、latency。
instances 实例与图谱页 本次写入的 Allmeta instances、planned links、created links、pending links。
replay 回放页 parent_audit_id、child_audit_ids、重跑原因、diff 摘要。

7.3 持久化策略

Postgres：操作型审计库 用于 /rule-check 列表、筛选、分页、详情页快速读取。现有 RuleCheckAudit 和 RuleCheckFlag 继续保留，并补充 page/block 概念。
Neo4j：语义图谱归档 把 RuleCheckAuditBook 写成实例节点，并用 instance links 连接 Candidate、Resume、Job_Requisition、Rule、Candidate_Match_Result。
对象存储：大文本正文 Prompt、raw response、超长 resume/JD 可存 MinIO 或等价对象存储，节点只保存 storage_ref、sha256、size。

规则检查审计书也要参与同一套 LinkPlanner / LinkWriter，只是需要在 AllmetaOntology 里补齐审计对象的 links schema：

(RuleCheckAuditBook rca_123)-[:AUDITS_RESUME]->(Resume R001)

7.5 写入时机

  1. RuleCheckAgent 先完成规则检查，得到 decision、flags、prompt、response、输入快照。
  2. 写 Postgres RuleCheckAudit / RuleCheckFlag，保证 UI 和运营查询可用。
  3. 把审计详情拆成 RuleCheckAuditPage / RuleEvidenceBlock，持久化正文或 storage_ref。
  4. 写 Allmeta 实例：RuleCheckAuditBook、pages、flags、evidence blocks。
  5. 把所有写入结果交给 LinkPlanner，生成审计书相关 instance links。
  6. LinkWriter 创建 links；失败时进入 pending，不影响 rule-check 主链路。
这里的审计持久化是合规和可追溯能力，不应依赖浏览器页面状态。页面只是读取这本已持久化的审计书。

8. AO 集成位置

8.1 推荐新增的内部模块

模块 职责 说明
AllmetaClient.createInstanceLink 封装 /api/v1/ontology/instance-links 替换旧的 writeLink(source_label, ...) 形态。
LinkSchemaProvider 加载并缓存当前 domain 的 links schema 优先从 Allmeta API 读取，开发环境可从 models/RAAS-v1/links_*.json fallback。
LinkPlanner 根据实例 payload + schema 生成 link 计划 纯函数，便于单测和 dry-run。
LinkWriter 执行 link 写入、处理 404/pending/重复 所有外部副作用集中在这里。
GraphWriteCoordinator 把 instance write 和 link write 串起来 供各 agent function 使用，避免每个 function 自己处理 links。

8.2 functions 的接入方式

每个 function 保持自己的业务逻辑，只改变写 Allmeta 的返回形态：

// 旧思路：写完实例就结束
await writeResume(payload)

// 新思路：写完实例后返回标准结果，再统一生成 links
const writes = []
writes.push(await writeCandidate(candidatePayload))
writes.push(await writeResume(resumePayload))

const plannedLinks = linkPlanner.plan(writes)
await linkWriter.write(plannedLinks)

8.3 写入顺序

  1. 先写所有实例节点。
  2. 确认实例写入成功，拿到标准 InstanceWriteResult。
  3. 基于成功写入的实例生成 link plan。
  4. 写 links。
  5. link 写入失败不应让业务 function 整体失败，除非该 link 是强一致必需。

这个顺序能保证：实例主数据优先落库，links 作为可重放的派生图结构处理。

9. 幂等、重试与 pending

9.1 为什么幂等是硬要求

AO 的 functions 运行在 Inngest / workflow 语义下，失败重试、局部 replay、手动重跑都是正常情况。 如果 instance link API 用 CREATE 而不是 MERGE，同一次业务写入重试会创建重复关系边。

当前 Allmeta instance-links handler 需要确认是否已经改为幂等。 若仍是 CREATE，上线前建议改为基于 linkKey 的 MERGE。

9.2 linkKey

每条实例关系都应有一个确定性 key：

linkKey = [
  domain,
  from.label,
  from.pk,
  relationType,
  to.label,
  to.pk
].join("|")

例子：

RAAS-v1|Candidate|C001|TARGETS|Resume|R001

Allmeta 侧最好用这个 key 做唯一约束或 MERGE 属性； AO 侧也可以在调用前先查 GET /instance-links 做防重，但最终幂等应由服务端保证。

9.3 pending link

如果 endpoint 不存在，LinkWriter 不应该创建 stub，也不应该让整个 function 失败。推荐记录 pending：

{
  "domain": "RAAS-v1",
  "linkKey": "RAAS-v1|Application|A001|RECORDS_PROCESS_FOR|Interview_Record|IR001",
  "linkName": "RECORDS_PROCESS_FOR",

pending link 可以存到 AO Postgres，也可以由 Allmeta 提供 outbox。选择哪边存，取决于谁负责重试。

9.4 失败处理策略

失败类型 处理方式
link-not-declared schema/API contract 不一致，记录 error，报警；不要自动降级成任意关系。
endpoint-not-found 记录 pending，等待 endpoint 实例创建后重试。
duplicate 如果 linkKey 相同，视为成功；如果属性不同，按最新 trace 更新属性。
neo4j-unavailable / 网络失败 短期重试；超过阈值后 pending，后续 backfill。
invalid-input 开发错误或 schema 字段错误，记录详细上下文并报警。

10. 历史数据回补

新方案上线前，Neo4j 中已经存在一批没有实例 links 的节点。它们不应该靠手写脚本一个个补， 而应复用同一个 LinkPlanner。

10.1 回补流程

  1. 按 domain 加载 links schema。
  2. 按 label 分页读取 Allmeta 实例节点，例如 Resume、Application、Candidate_Match_Result。
  3. 把每条实例包装成 InstanceWriteResult 形状。
  4. 调用 LinkPlanner 生成计划。
  5. dry-run 输出总数和样例，确认无误。
  6. 批量调用 LinkWriter，依赖 linkKey 保证幂等。
  7. 输出回补报告：planned、created、already_exists、pending、failed。

10.2 dry-run 报告样例

{
  "domain": "RAAS-v1",
  "schemaVersion": "links_v0_1_064",
  "labelsScanned": ["Resume", "Application", "Candidate_Match_Result"],
  "instancesScanned": 1842,
  "linksPlanned": 2679,
  "willCreate": 2410,
  "alreadyExists": 206,
  "pendingEndpoint": 63,
  "errors": []
}

11. 观测指标

每次 function run 或 batch backfill 至少记录这些指标：

指标 含义
instances_written 本次成功写入 Allmeta 的实例数量。
links_planned LinkPlanner 根据 schema 推导出的关系数量。
links_written 成功创建或幂等命中的关系数量。
links_pending 因为 endpoint 暂不存在而进入 pending 的关系数量。
links_skipped 因为缺 FK、schema 不支持、空字段等被跳过的数量。
links_failed 真实失败数量，需要报警或排查。
audit_books_written 成功持久化的规则检查审计书数量。
audit_pages_written 成功持久化的审计页数量，至少应覆盖 cover、input、selection、judgment、prompt、response、instances。
audit_large_blocks_externalized 被写入对象存储并以 storage_ref 引用的大文本块数量。
audit_graph_links_written 审计书到候选人、简历、岗位、规则、结果、页面、证据块的图关系数量。

日志里建议带上 domain、schemaVersion、linkKey、 schemaLinkId、auditId、pageId、traceId、runId， 方便从 AO run 追到审计书页面和 Neo4j 边。

12. 落地 checklist

AllmetaOntology 侧

  • 确认 /api/v1/ontology/instance-links 在目标环境可用。
  • 确认 schema lookup 能识别 RAAS links schema 中的关系：link_name / action / relationship type 必须统一。
  • 将 instance link 创建从 CREATE 改成基于 linkKey 的 MERGE，或提供服务端幂等能力。
  • 确认 DataObject primary key 可被 API 正确解析，例如 Candidate.candidate_id、Resume.resume_id。
  • 补齐审计书相关 DataObject：RuleCheckAuditBook、RuleCheckAuditPage、RuleEvidenceBlock、PromptSnapshot、ResponseSnapshot。
  • 补齐审计书 links schema：audit book 到 Candidate / Resume / Job_Requisition / Rule / Candidate_Match_Result / pages / flags / evidence blocks 的关系。

AO 侧

  • 让所有 Allmeta instance writer 返回标准 InstanceWriteResult。
  • 新增 LinkSchemaProvider，缓存 domain + version 对应的 schema links。
  • 新增纯函数 LinkPlanner，只处理带 FK evidence 的 object links。
  • 新增 LinkWriter，写入 /instance-links，处理 pending 和幂等命中。
  • 在主要 agents 写实例后接入 link generation：resume parser、create JD、rule check、match resume、interview inviter。
  • RuleCheckAgent 写审计时，要把审计拆成多页书：cover、input_snapshot、rule_selection、rule_judgment、evidence、prompt、response、instances、replay。
  • 审计大文本要持久化 storage_ref + sha256 + size，避免只存在前端内存或单个超大 Neo4j property 中。
  • 增加 dry-run 和 backfill 命令，先对历史实例做报告，再批量创建 links。

推荐实施阶段

阶段 目标 产出
Phase 1 对齐 Allmeta API contract linkName 规则、幂等策略、endpoint 可用性确认。
Phase 2 实现 AO dry-run LinkPlanner 不写 Neo4j，只输出将创建哪些 links。
Phase 3 接入运行时写入 functions 写实例后自动创建 links，失败进入 pending。
Phase 4 历史数据回补 对已有实例批量补齐 links。
Phase 5 治理和监控 指标、报警、schema version drift 检测。
最终目标：AO functions 只产生实例事实；实例之间的图关系由 AllmetaOntology links schema 驱动生成。 这样图结构与 ontology 同步演进，避免 AO 代码里散落硬编码关系名。
