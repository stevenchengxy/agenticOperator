01一次调用的全貌

每个在招岗位（JR）跑一次。智能体把岗位 + 候选人简历 + 命中的规则拼成提示词，交给大模型逐条判定，模型只返回「每条规则的 status」，最终「通过 / 未通过」由 server 端折叠计算 —— 模型不下结论。

输入装配
ruleCheckAgent buildRuleCheckInput → runRuleCheck
从 partner-pg 取岗位、回拉简历、按 client/部门从本体拉「命中的规则」，预取 Neo4j 图谱上下文。
system + user + tools chatComplete(maxTokens 16000)
大模型
逐条规则判定 status ∈ {pass · fail · insufficient_info · not_triggered · pending · not_executed}
按 §5 决策树独立评估每条规则；可在 5 轮内回查图谱（tools）；输出纯 JSON。
{ "rule_results": [...] } 必须每条规则各一条目
server 结算（与模型无关）
foldDecision fail-closed
任一 fail，或底线规则上的 insufficient_info / pending → 未通过；否则 通过。

02① System Prompt （≈420 字，逐字）

你是一名 matchResume 规则评估员。

严格按照 user 消息中的 INPUT / GRAPH_CONTEXT / RULES 评估，输出严格符合 schema 的 JSON。

边界约束：
- 必须按 Set 顺序、Set 内列出顺序评估，每条 rule 都独立评估并输出 status（不要因为前面有 fail 就把后面标 not_executed）
- 严格按 user 消息中第 5 节的"单条 rule status 决策树"判断 status
- 任何 fail 必须在 reason 中引用 GRAPH_CONTEXT 里的具体字段+数值；做不到的标 insufficient_info
- 字段为 null / 缺失 / 空数组 → insufficient_info，绝对不要判 fail
- 必须输出合法 JSON，不要在 JSON 外加任何文本（包括 markdown code fence）

03② User Prompt（§1–§8）

§1 角色
# matchResume Rule Check
## 1. 你的角色
你是一名 matchResume action 的规则评估员。基于给定的 INPUT、GRAPH_CONTEXT 和 RULES，
按 Set 顺序逐条评估每条 rule 的 status。你只输出每条规则的 status，不要输出或结算最终
decision —— 最终 decision 完全由 server 端依据各 rule 的 status 统一汇总（见 §6）。
- 必须严格按 Set 顺序、Set 内列出顺序评估。
- 不要给候选人打匹配分数（评分由下游算法负责）。
- 不要在 reason 中编造 INPUT 或 GRAPH_CONTEXT 中未提供的信息；缺字段一律标 insufficient_info。

§4 Rules — 每条规则的渲染格式（真实命中 5 条；示一条）
## 4. Rules to check — 严格按 Set 顺序、Set 内严格按列出顺序评估
> 执行约束（违反即视为输出无效）：① Set 间按 §4.1 → §4.2 顺序，不得跳过/乱序

### 4.1 Set 1 — validateRedlineAndBlacklist  [order=1]
#### Rule 10-25: 华为荣耀竞对与客户互不挖角红线  [applicableClient=通用, enforcement=mandatory, onFail=block]
- submissionCriteria: 候选人简历已完成解析，工作经历数据已结构化。
- logic: 系统在简历匹配环节，自动检索候选人工作经历中是否包含华为、荣耀及其关联公司的

（其余 10-26 / 10-45 / 10-46 / 10-42 同此格式逐条列出）
§5 单条 rule 的 status 决策树 — 判断精度的核心（逐字）
## 5. 单条 rule 的 status 决策树（严格按下列顺序判断，命中即止）
1. rule 触发条件不成立 → not_triggered
   （server 已按 client+部门过滤一轮，但你仍须按 rule 文案的"针对 X 客户/事业群/候选/岗位"
    限定再校验一次；明显不落在限定内 → not_triggered，reason 写明不匹配维度）
2. 要评估的字段在 GRAPH_CONTEXT 中 null / 缺失 / 空数组 → insufficient_info
   （重要：缺字段 ≠ 不满足。slot 为 null/[] 一律视为"信息不全"，绝对不要判 fail）
3. 字段存在且明确不满足 → fail（必须在 reason 引用 GRAPH_CONTEXT 的具体字段+数值）
4. 字段存在且满足 → pass
5. 需 HSM 主观判断、无法自动结算 → pending
⚠ 极性陷阱（排除类/冷冻期/竞对/黑名单）：命中坏条件→fail；未命中→pass，极性相反最易判反。
   "离职满6个月→未命中→放行→pass"（别因 reason 里"满足"二字打 fail）；"离职仅3个月→fail"。
⚠ 最常见错误是把 insufficient_info 误判为 fail。判 fail 前再自问：引用的字段真的非 null 吗？
§6 决策结算 · §7 输出 schema · §8 自检（逐字，要点）
## 6. 决策结算（由 server 计算，与你无关）
最终 decision 完全由 server 端依据各 rule 的 status 汇总；你只输出 rule_results[]，不要输出 decision。

## 7. Output schema  仅输出严格符合下列结构的 JSON，不允许 markdown 代码块、不允许多余字段：
{ "rule_results": [ { "rule_id": "<id>", "status": "<status>", "reason": "<判定依据>", "next_action": "<action>" } ] }
- status ∈ {pass, fail, pending, insufficient_info, not_triggered, not_executed}
- next_action ∈ {continue, block, supplement, review}，必填，按 status 取值
- 每条规则都必须有一条对应条目，按 Set 顺序输出；reason 各 status 都必填
- 不要输出 rule_name / step_id / decision / stats / explanations（runner 会重算）

## 8. 自检  [ ] 按 Set 顺序？ [ ] 每条规则各一条目（数量必须与规则总数一致）？
[ ] 每条 fail 都引用了具体字段+数值？ [ ] 所有 null/缺失 标 insufficient_info 而非 fail？ [ ] 仅输出 JSON？

05④ 输出 Output + server 结算

大模型返回的真实样本（取自生产日志，prompt_tokens=5035 · completion=206 · finish=stop · tool_rounds=0）：

{
  "rule_results": [
    { "rule_id": "10-25", "status": "pass",
      "reason": "钱八简历显示最近两段经历为美团(2024.04-2026.04)及字节跳动(2020.07-2024.03)，无华为/荣耀任职记录，未命中竞对冷冻期，放行。",
      "next_action": "continue" },
    { "rule_id": "10-26", "status": "pass",
      "reason": "…无OPPO/小米任职记录，未命中竞对冷冻期，放行。", "next_action": "continue" }
  ]
}
server 结算（foldDecision）：校验条数 == 规则数 → 任一 fail 即「未通过」；底线规则上的 insufficient_info / pending 也折成「未通过」（fail-closed）；否则 通过。本例两条 pass → 通过。
⚠ 条数必须严格相等：模型少返/多返一条 → parse-error → 整个 run 挂起（park），不出判断。

06⑤ 精准度审计 （5 视角对抗审计 × 真实日志：9 个真实候选人 / 664 条 response）

够用，但有
已知精度风险

单条规则的 LLM 判断本身是准的（reason 连贯、引对字段）。不准的是端到端——系统性把"没违规"折成候选人「未通过」（误拒 / false FAIL）。真实候选人里抓到 6 次「零确认违规却未通过」。

且三大主因都不在 prompt 格式，而在折叠逻辑（foldDecision）和图谱取数（graph.resume）。也就是说："现在的格式"判得准；不准出在别处。

三大已证误拒机制

致命底线规则字段在图谱里根本不存在 → 静默未通过瘦身无关
怎么误判
规则 10-35（强制+block=底线）看候选人 nationality，但该字段在 9 个真实候选人里 0 个存在。模型正确返回 insufficient_info，foldDecision 把底线规则上的 insufficient_info 无条件折成「未通过」。好候选人被静默、不可挽回地拒掉。
真实证据
d52a569b（陈思）：4 pass + 1 not_triggered + 1 insufficient_info（10-35 缺 nationality）→ 整体 FAIL。decision=FAIL，stats.fail=0。
高简历选行不确定 → 取到空简历 → 全部 insufficient_info瘦身无关
怎么误判
graph.resume 只按 candidate_id 取、不带 resume_id、不排序、blind rows[0]。多简历候选人可能拿到 experience 为空的那行 → 简历类规则全 insufficient_info → 未通过。resume_id 在 runner 里有，却没传进 buildGraphContext。
真实证据
mirror-dup-chensi：resume.experience='' → 10-25/10-26 insufficient_info → FAIL（零确认违规）；同一个人别处 experience 长度 1336（正常）。
高极性翻转：写"满足放行"却盖章 fail，server 原样信任瘦身无关
怎么误判
模型把离职间隔算对了，reason 写"已满6个月，满足放行条件"，却盖 status=fail。coerceRuleResults 只校验 enum + reason 存在、无 reason↔status 一致性校验；10-42 是底线规则 → 翻转的 fail 直折成终态「未通过」，无人工兜底。§5 有极性警告，但纯劝说没挡住。
真实证据
3 次 10-42 status=fail 的 reason 全是放行结论；同一输入上 10-42 分布 = { not_triggered:13, fail:6, pass:5 }。

瘦身有没有伤精度？

净结论：没有。上面 3 个致命/高危全部 slim-neutral —— 住在 graph-context.ts / foldDecision / coerceRuleResults，把 JR 拉回完整版一个都救不了。瘦身对输出鲁棒性反而有益（输入压到白名单 → 0/664 截断）。
唯一一处瘦身回退：删 client_name（原带「字节 / 腾讯」）只剩 UUID，且没注入 server 已算好的 business_group_resolved / client_name_resolved → BG / 部门维度的底线规则（10-42 / 10-43 / 10-40）靠模型从英文 sd_org_name='Technology' 瞎猜，来回摇摆。修法是注入那两个字符串进 §2.1，而不是回退白名单。

全部风险（按严重度）

风险严重度瘦身影响
① 结构性缺字段（nationality）fail-close致命中性
② 简历选行不确定 → 空简历高中性
③ 极性翻转无一致性校验高中性
④ BG / 客户维度未注入（模型靠英文 org 瞎猜）高变差
⑤ 数据缺失型 FAIL 与真违规无法区分中中性
⑥ 条数严格相等：一条坏 → 整批 park中变好
⑦ 规则元数据缺失默认偏 fail-closed低中性
⑧ 数据稀缺时误读规则意图（10-25 当年龄规则）低略差

07⑥ 推荐修复（按收益排序）

1
🔴 别再用结构性缺失的数据 fail-close
foldDecision：底线规则若所需字段在预取图谱里根本不存在（10-35 的 nationality、空简历）→ 走「需人工复核 / 待补数据」而非静默未通过；并在 graph.resume 为空时回退到现在被丢弃的 input.resume（刚解析、已过闸门的简历）。→ 直接消掉第 ①②类误拒。
2
🟠 修简历选行 + 注入解析维度
buildGraphContext 传入 resume_id 精确取简历（回退优先非空 experience）；把 business_group_resolved + client_name_resolved 渲染进 §2.1（顺手补回瘦身删掉的客户名）→ 修第 ④类摇摆。
3
🟠 加确定性极性 + 解析护栏
coerceRuleResults：status=fail 但 reason 是放行措辞 → 判极性矛盾，降级 / 转人工 + 记可统计事件；status 大小写/同义词归一，缺条目从 steps 回填，避免「少一条 → 整批 park」。
一句话："现在的 prompt 格式"判得准；不准主要在折叠逻辑和图谱取数。修精度应动 foldDecision / coerceRuleResults / graph-context.ts，而不是只调 prompt。瘦身保留即可。
