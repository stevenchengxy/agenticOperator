Agentic Operator · Macro Architecture

不是一套 Harness，
而是一群会协作的 Harness

一个顶层「元编排大脑」统一调度若干专精 Harness：一套动态生成新智能体、一套管理与挑选预先写好的智能体、一套真实执行事件链。它们说同一种「本体事件」语言，产出的每个智能体都是可互换的节点 —— 让系统既能即兴造人，又能复用老兵，由一个大脑统一编排成军。

01 · 核心洞察

把「Harness」本身当成可组合的单元

今天我们有一套很强的生成 Harness（Agent 工厂 v3 大脑）：它读业务本体、自己设计 → 写代码 → 沙箱验证 → 交付智能体。但一套 Harness 再强，也只擅长一件事。真正的跃迁是把 Harness 本身变成可被更高层调度的积木：

动态生成

没有现成的智能体？生成 Harness 临场造一个 —— 从本体动作派生、AI 亲写 prompt 与代码、沙箱跑通才交付。

预设选择

已经有写好/造好的智能体？选择 Harness 从智能体注册表里按能力与事件签名挑出最合适的来复用。

统一编排

元编排大脑 把目标拆成子目标，逐个决定「造还是用」，再把所有节点（无论谁产出）编成一张可执行的事件链 DAG。

关键统一点：无论一个智能体是 AI 临场生成的、还是人提前手写的，它对元编排大脑都长得一模一样 —— 都是一个绑定本体事件（trigger→emit）的 Inngest 函数节点。正因为节点契约统一，不同 Harness 的产物才能拼成一条链。这就是整套架构能成立的地基。
02 · 三层架构

元编排 → 专精 Harness → 共享基座

顶层一个大脑负责「想清楚要什么、谁来做」；中层是各司其职的 Harness；底层是所有 Harness 共享的本体、工具库、注册表、事件网格与审计。控制流自上而下派发，数据流自下而上回灌。

03 · 统一节点契约

一个节点，长一个样 —— 不管谁造的

能让多套 Harness 拼成一条链的唯一原因：它们的产物都遵守同一个节点契约。每个智能体都是一个绑定本体事件的执行单元 —— 消费某些 trigger 事件、产出某些 emit 事件，中间用自己的 prompt + 工具 + 决策逻辑。对编排者来说，「AI 临场生成的」和「人提前手写的」无差别，都只是一个有事件签名的盒子。

这正是当前已成立的部分：工厂生成的智能体、和 server/inngest/agents/*.ts 里人手写的智能体，都是 Inngest 函数、都用本体事件名 trigger/emit。所以它们本来就能在同一条事件链里接力 —— 缺的只是上面那个「注册表 + 元编排」把它们当成同质节点统一调度。
04 · 核心智能

Build-vs-Reuse：造一个，还是用现成的？

元编排大脑最核心的判断：面对一个子目标，先问注册表有没有现成能干这活的智能体。有 → 选择 Harness 直接绑定复用（快、稳、省）；没有或不够好 → 派生成 Harness 临场造一个，造完必须过验收 Harness，再回写注册表沉淀下来。下次同样的活就能复用了 —— 系统越用越聪明。

07 · 演进路线

从「一套会造的」到「一群会协作的」

不需要推倒重来 —— 现有的工厂、Inngest、本体、验收门都是这套架构的合法零件。按四步增量演进：

P0现状
一套生成 Harness。工厂 v3 能从本体造出一支域内智能体并沙箱验证。预写智能体散落在 server/inngest/agents，未被统一编目。— 已在跑。
P1统一注册表
建「智能体注册表」：把预写 + 生成的智能体统一编目（能力、域、trigger/emit 签名、状态）。这是后面一切的地基 —— 让节点对编排者同质化。
P2选择 Harness
加路由器：给定子目标的事件签名，从注册表检索最匹配的现成节点。先做确定性匹配（事件签名 + 域），再叠 LLM 语义排序。
P3元编排大脑
顶层 conductor：拆目标 → 逐子目标 Build-vs-Reuse → 组装跨 Harness 的节点 DAG → 调执行+验收 → 失败重规划。复用现有 ReAct 循环 + 行为门作骨架。
P4自我增强
闭环沉淀：生成出来的好节点回写注册表、跨域复用；跨次反思喂养造/用决策；人在环路贯穿全层。系统越用越聪明。
08 · 为什么这样设计

站在成熟范式的肩膀上

Orchestrator–Workers

顶层大脑拆解目标、派发给专精 worker（这里 worker 是「一整套 Harness」）—— 和多智能体研究系统的「主管+子代理」同构。

Supervisor / Router

选择 Harness 就是一个 agent 路由器：按能力把活路由给最合适的现成节点，而非每次从零生成。

动态技能合成 (Voyager 式)

生成 Harness + 注册表沉淀 = 把一次性产物变成可复用技能库，自我扩充能力边界。

编排 × 编织 (Orchestration × Choreography)

元编排大脑负责「想清楚顺序」，事件网格负责「自治地接力」—— 计划集中、执行去中心，兼得可控与弹性。

Verifier-in-the-loop

任何被组装的节点集都要过行为级验收（真跑通才算数），把「过编译/图闭合」与「逻辑正确」分开。

Human-in-the-loop

人可在任一层注入消息，大脑自由分析/重规划/调工具 —— 机器拦不达标，人拦方向错，双保险。

09 · 诚实的边界

这套愿景里，还没闭合的几道缝

① 运行物 ≠ 验收物。当前沙箱跑的是通用执行器（读 spec），AI 亲写的 .ts 不直接执行。要真把「Agent-as-code」做实，得让运行时在隔离 worker 里执行那段代码（连带需要 Firecracker/gVisor 级沙箱）。
② 注册表是新地基，得先建对。能力描述、事件签名、版本、域、状态要规范化；选择 Harness 的匹配质量完全取决于它。
③ 成本与隔离。多层 Harness + 子代理会放大 token 与延迟；递归编排需要预算计量、深度上限、可中断。
④ 验收要更硬。除了「全链路跑通」，还需分支覆盖、N 次重跑方差、降级硬失败 —— 才能证明一支编队是稳的，不只是「跑过一次」。

一句话总括

把每套 Harness 当成会一件事的专家，给它们一个共同的母语（本体事件）和一本共同的花名册（注册表），再派一个总指挥（元编排大脑）按「造还是用」临场点将、编队、验收、上阵 —— 这就是从「一个会造 agent 的工厂」长成「一支会自己组织、自己造人、自己打仗的智能军团」的路径。
