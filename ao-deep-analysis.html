AO 真正在变成什么 三层物种

AO 表面上是"招聘 AI 控制台",但代码里真正在长出来的是一个三层物种:① 一个事件驱动的多域运行底盘(Inngest + Postgres archive 写穿 + 双写 partner-pg/Neo4j),招聘域 6 个真 agent 在上面跑业务,能源/费控 28+14 个 agent 由 ontology snapshot 派生;② 一个确定性优先的监控控制平面(blackboard 模式,LLM 只采样陪审,critical path 不依赖网关),Notification 是 system of record 而不是派生流;③ 一个最近三周才长出来的"自主大脑"(Agent Factory v3),它已经不是确定性流水线,而是一个 60-turn / 600k-token 的 ReAct 循环,带 FailureReflection 跨 run 学习、refine_agent diff、sandbox_run 真部署到隔离 Inngest 域、score_spec A-D 评级。三个层在代码里是清楚分层的(v3 → {v2 deploy, gen persist}),但在用户故事里还没有合体——Fleet 承诺的三柱(Monitor/Manage/Behavior)只有 Monitor 真的能用,Behavior 是 v3 在 /tools 路径下独立生长,Manage(暂停/回滚/RBAC/审批闸)基本是空的。AO 不是 LangGraph 的竞品,也不再只是"招聘工具",它在变成一个"领域本体 → 自主生成 agent → 运行 → 可观测 → 治理"的端到端 vertical platform,但目前仍只有招聘域是真的、其他两个域是 snapshot-driven 的演示。

①
事件驱动的多域运行底盘 招聘域真生产
Inngest + Postgres write-through archive + 双写 partner-pg / Neo4j。招聘域 6 个真 agent 在跑业务（~4000 行业务代码 + 18 个手写工具 + dependency-health 分类），能源 28 个 + 费控 14 个 agent 由 ontology snapshot 派生（演示，未真生产）。
②
确定性优先的监控控制平面 已成熟
Blackboard 模式：lib/monitor/* 是纯算法（health / sla / cost / error-rate）；LLM 只采样陪审（rule-check 才用 LLM 且二次 verify）；critical path 不依赖 LLM 网关。Notification 是 system of record（@@unique dedupeKey），不是派生流。
③
自主 ReAct 大脑（Agent Factory v3） 最近三周长出
60-turn / 600k-token 的 ReAct 循环。带 FailureReflection 跨 run 学习（DB 表当 episodic memory）+ refine_agent 结构化 diff + sandbox_run 真部署到隔离 Inngest 域 + score_spec A-D 评级。三层分层清楚（v3 → v2 deploy + gen persist），但跨域生成至今未在非招聘域端到端跑通——这是叙事和证据最大的 gap。

真实的强项 7 项，全部带证据

✓
确定性骨架 + LLM 增强的分层架构,在 LLM 网关挂了也活着

✓

✓

✓

evidence tools/index.ts:417-508 refine_agent 保留 attemptHistory[actionName] + 结构化 diff(systemPromptChanged/toolsAdded/toolsRemoved/decisionLogicChanged);tools/index.ts:243-290 sandbox_run 真部署到隔离 Inngest 域并流式 deploying→deployed→firing→polling→settled;tools/index.ts:749-772 score_spec 给 A-D 等级。这不是'AI 生成 agent'的 demo,是带审计闭环的工程系统。

值得标注的创新模式 7 项可迁移 pattern

这些不是「写了个 ReAct 循环」级别的基础能力。审计员把它们标记为同行框架里少见、有迁移价值的真创新。如果以后做 OSS 或对外分享，主打这些。

★
FailureReflection 作为持久化的跨 run 课程,自动织进下次 system prompt
why novel: 大多数 LLM agent 系统要么靠 chat history(每次重启清零),要么靠人手维护 prompt。AO 把'失败原因'结构化进 DB(kind/summary/rootCause/lesson),取最近 8 条注入 system prompt。这是数据库表当 episodic memory 用,且大脑必须写 reflection 才能 finish(兜底自动合成)——把'agent 学习'变成可审计的工程闭环。
可迁移到: 任何长生命周期的 autonomous agent 系统(coding agent、ops agent、research agent)。比 vector memory 更可解释,比 system prompt 手工迭代更自动。
★
Write-through middleware + 轮询对账的耐久性双路径
why novel: Inngest 默认是事件总线,持久化靠它自己。AO 用 middleware 在 send/run-start/run-complete 时直写 Postgres archive,30s 轮询是兜底对账。读端 live∪archive 合并,live 优先 archive 补全。这破解了'实时 vs 耐久'二选一,实时性来自 live,耐久性来自 write-through 不是 poller。
可迁移到: 任何'事件引擎(Inngest/Temporal/SQS)+ 自己想留审计'的项目。也适用 Stripe webhook、Kafka consumer 想做 exactly-once-ish 审计的场景。
★
Reasoning 作为工具调用的一等公民参数
why novel: P1_TOOLS 里每个工具(design_agent/refine_agent/sandbox_run...)都要求 reasoning 字符串(>150 字符),会被 stream 给用户、存进 ledger、作为大脑'思考过程'展示。大多数 tool-use 系统只关心输入输出,AO 把'为什么调'变成强制 schema 字段,直接让 ReAct 的 thought 变成可审计的结构化数据。
可迁移到: 任何 high-stakes 的 agent 决策系统(医疗、金融、合规)。把思考过程从'LLM 自然语言'变成'工具 schema 的 required field',审计成本指数级下降。
★
refine_agent 的 attemptHistory + 结构化 diff
why novel: 大脑改自己写的 agent 时,旧 spec 保留在 attemptHistory[actionName],并 emit { systemPromptChanged, toolsAdded, toolsRemoved, decisionLogicChanged } 的结构化 diff,而不是 'LLM 自己说改了什么'。下次 refine 大脑可以 diff_spec 看自己上一轮做了什么。这是 AI agent 版本的 git log + diff。
可迁移到: 任何让 LLM 改代码/prompt/config 的产品(Cursor、Devin、Aider 风格)。把'改了什么'从自然语言变成结构化 patch,后续 agent 可以 grounded 推理。
★
Sandbox 真部署到隔离 Inngest 域 + 多阶段流式进度
why novel: Factory v3 的 sandbox_run 不是 dry-run mock,而是真把生成的 agent 部署到 agentic-operator-<test-domain> 隔离 Inngest 实例,fire 真事件,polling 真 run,5 阶段(deploying→deployed→firing→polling→settled)流式给用户。这是把 SWE-bench 风格的真执行验证嵌入 ReAct loop。
可迁移到: 任何'生成代码/agent 后想证明它真能跑'的系统。比 LLM 自己说'我写的对'强百倍,适合 codegen + autonomous repair 类产品。
★
Blackboard 监控 + 域内自治分级(read_only/notify/act)
why novel: Multi-Agent Monitor 设计明确反对'super-monitor'(15× token 成本);改用 sweeper fan-out 到独立确定性监控(health/sla/cost/error-rate),Postgres 是 blackboard。每个域有自己的 MonitorConfig(autonomy 三档),允许 staged rollout(read_only → notify → act)而不动 agent 代码。
可迁移到: 任何多 agent / 多服务的 SRE 系统。这是把 'AI ops' 从'让 LLM 看全部日志'拉回'确定性监控 + LLM 采样陪审'的清醒架构。
★
Dual-write contract 显式标在工具 schema 的 sideEffect tag
why novel: lib/tools/recruitment-tools.ts 每个工具都有 sideEffect: 'read' | 'write' | 'dual-write' 标签,把'这个工具会写两个系统'从隐式语义变成 schema 显式契约。生成 agent 的大脑能看到 sideEffect 选 tool,审计能据此过滤,validate 能据此预防。
可迁移到: 任何 multi-system 写场景(微服务 + 外部 SaaS、CRM + DB 双写)。把副作用元数据带在工具 schema 上是 agent 时代的合规基础设施。

具体建议 10 项，按 P0/P1/P2 排序

每条都是具体行动（cite 改哪个文件 / 加哪个字段），不允许「improve」「enhance」这种空动词。Effort 标 small / medium / large。

P0 small 给 LLM 成本加 per-run 硬熔断 + per-customer rate limit
具体做什么
在 server/inngest/factory/agent-executor.ts 和 v3 conductor.ts 加 token-per-run 上限(建议 100k 招聘、200k factory),超出抛 NonRetriableError;在 lib/monitor/cost.ts 之外加请求级 rate limit(per domain + per clientId,Postgres counter + Redis 替代品);FactoryLlmCall 记录后立刻校验是否越界。
为什么现在
现在只监控不限制,v3 brain refine 卡住能在 5 分钟内烧 600k token;一个被泄露的 FACTORY_ADMIN_TOKEN 加无限循环可以一夜花完云预算。这是落地中型客户前必须先关的洞,优先级超过任何新功能。
解锁什么
可以真敢把 v3 brain 开给运营人员用,也是 multi-tenant 落地的前置。
P0 medium 把 clientId 从 post-fetch 过滤改成 Prisma where 强制注入
具体做什么
在 lib/db 包一层 tenantScoped(prismaClient, clientId) 工厂,所有 model 的 findMany/findFirst/update/delete 自动注入 where: { clientId },原始 prisma 只允许在审计内部使用;同时给 Candidate/Resume/CandidateMatchResult/RuleCheckAudit 加 @@index([clientId]) 和考虑加 @@unique([clientId, businessKey])。
为什么现在
app/api/monitor/overview/route.ts:52-67 和 rule-check-audits/route.ts:113,217 现在是把所有客户数据 load 进内存再 filter——一次 SQL 注入或一次代码改错,所有客户的候选人 PII 互相可见。招聘=GDPR 监管域,这是法务级 P0,不是技术债。
解锁什么
真正的多租户能力 + 合规初稿,直接决定 AO 能不能卖给第二个客户。
P0 medium 用 v3 brain 真生成一个非招聘域的真 agent(费控或能源),端到端跑通
具体做什么
选费控-v1 一个简单 action(比如'发票 OCR + 校验金额'),让 brain 从 read_ontology 一路生成→sandbox→真部署→handle 真事件。如果跑不通,把失败 root cause 落 FailureReflection,这是叙事和现实的真实差距。不要再优化招聘域。
为什么现在
现在能源/费控是 snapshot-driven 演示,招聘 6 个 agent 是手写的——'v3 能跨域生成'还没有被证明过。这周不证就永远证不了,叙事会越来越虚。这一次跑通(或失败)决定 v3 是平台还是 demo。
解锁什么
如果成功:有真凭据说 AO 是 vertical agent platform。如果失败:知道真正的瓶颈在 tool registry / ontology 表达力 / 还是 brain 的推理边界。
P1 small 写一份 docs/agent-factory/README.md 说清 v2/gen/v3 的边界
具体做什么
一页图 + 一段话,回答:v2 是不是死的?gen 是不是底层?v3 是不是主线?import 关系图标出 v3→{v2.deploy, gen.persist}。同时 deprecate 不再活跃的 builder(planner/critic 如果 v3 不调就标 @deprecated)。
为什么现在
新工程师(包括 6 个月后的你自己)读 lib/agent-factory-* 找不到入口。git log 显示 3 天 4 phase commit,blame 已经不可读。这一步是把'三周冲刺出来的 v3'变成可维护资产的最小投资。
解锁什么
降低 bus factor + 给招聘对外宣讲一份不撒谎的架构图。
P1 medium 把 RuleCheckAudit 加 domain 列 + 抽出 RuleCheckEngine 接口
具体做什么
schema.prisma 给 RuleCheckAudit 加 domain String,migrate 历史数据全填 'recruitment';lib/rule-check/ 提取 RuleCheckEngine interface { evaluate, audit, replay };招聘的 LLM 实现、能源的 deterministic 实现、费控的 policy 实现都 implement 它;按 domain dispatch。

P1 medium 把 FactoryV3Content 拆成 5 个子组件 + 给 P1_TOOLS 写 hermetic 测试
具体做什么
components/behavior/factory-v3/ 拆成 FactoryChat / RightPanelAgents / RightPanelTrace / RightPanelKnowledge / RightPanelEval;FV3_CSS 158 行进 .module.css。lib/agent-factory-v3/tools/index.ts 13 个工具每个写 vitest(mock ctx + 验证 emits/persist/state mutation),先覆盖 design_agent/refine_agent/sandbox_run 三个最重的。

P1 medium 兑现 Manage 柱的 MVP:暂停 + 软回滚 + 审批闸
具体做什么
Fleet 上的 Behavior'+ Deploy' 现在指向'contact RAAS'占位,改成走 v3 brain;但 brain 产出的 spec 默认 status='draft',加一个 /api/agents/[slug]/promote 端点带 reason 字段、写 AuditLog。Agent detail drawer 加 'Rollback to v{n}' 按钮(AgentVersion 已经有历史)。
为什么现在
Fleet 副标题宣示三柱已经一年了,Behavior 在 /tools 路径独立长,Manage 完全是空的。运营人员现在没法用 AO 真治理 agent——这正是把'招聘工具'拉成'agent fleet platform'最缺的那一截。
解锁什么
真正能对外说'AO = Monitor + Manage + Behavior'。
P2 medium 给 partner-pg 双写加 outbox + 重放队列
具体做什么
新增 PartnerPgOutbox 表(eventKey, payload, status: pending/sent/failed),所有 partner-pg 写先进 outbox,再异步刷;失败有自动重试 + DLQ;match-resume / rule-check 不再因为 partner-pg 慢就把 run 阻塞。
为什么现在
现在 partner-pg 慢 → agent 卡 → Inngest 重试 → 雪崩。outbox 模式让本地决策不被 partner SLA 拖死,也给将来 RAAS 解耦留路。
解锁什么
可以承诺 SLA 给招聘客户,partner-pg 故障 < 5 分钟时业务无感。
P2 small 把 reasoning + diff + reflection 做成一个'agent build report' PDF
具体做什么
v3 一次 brain 跑完后,从 BrainEvent ledger 渲染一份带 reasoning trace、refine diff、sandbox 结果、score_spec、final reflection 的 PDF/HTML 报告,发邮件给运营或挂在 /tools 历史。
为什么现在
你已经把 reasoning 当一等公民、diff 结构化、reflection 持久化——这些数据现在只活在 SSE 流里,scroll 走就没了。变成可下载工件就是销售素材(展示给客户'看这是 AI 怎么造你的 agent'),零额外成本。
解锁什么
把工程亮点变成 GTM 武器,Factory v3 三周冲刺的 ROI 才回来。
P2 medium Prometheus /metrics endpoint + cost forecasting
具体做什么
暴露 /api/metrics(Prometheus 格式)export agent run count / token spend / dependency error rate / queue lag;cost.ts 加 7 天趋势 + linear projection,在 budget 80% 时告警(不是 100% 越界才告警)。
为什么现在
SRE 想接 AO 进 Grafana 现在只能 query Postgres;cost 现在只查越界、不查趋势——增长曲线 1% 也能 3 个月烧光。中型客户 ops team 第一个问的就是 metrics。
解锁什么
标准 SRE 工具链对接 + 财务可预测。

3 个战略选项 互斥，要选

这三个方向都被代码里的某些投入支撑着，但不能同时做。哪条最适合取决于你想让 AO 在 3 年后是什么。

深耕招聘 RPO,把 AO 做成中国最强的招聘 AI 控制台
📌 你在赌
招聘域已有 6 个真 agent + 18 个手写工具 + dual-write 契约 + dependency-health,继续把 Manage 柱(RBAC、审批、回滚、合规审计)和招聘特有的 rule-check 体系(职级套差、归属锁定、冷冻期)做深;v3 brain 改造成'招聘专属顾问',Factory 不强求跨域。卖给中型 RPO + 中大型 HR 部门。
⚠ 放弃什么
放弃'通用 agent fleet platform'叙事,不和 LangGraph/CrewAI 在抽象层竞争;能源/费控域作为研发资本而不是产品线;TAM 受限于招聘 RPO 市场。
💡 为什么值得考虑
这是唯一已经被代码证明的事:6 个 agent 在生产、partner-pg 双写在跑、rule-check 复杂 prompt 反复迭代过。其它两个域全是 snapshot-driven 演示。商业上'第一个客户落地'永远是最难的,在已经接近落地的方向继续推阻力最小。
把 Agent Factory v3 拆出来做成独立的 agent-codegen 平台
📌 你在赌
v3 brain 的 reasoning-as-first-class-param、refine_agent diff、sandbox 真部署、FailureReflection 跨 run 学习——这些 pattern 是真创新,且通用。把 v3 独立成 SaaS / 开源项目(给定 ontology 生成 Inngest agent),招聘 AO 变成 v3 的 reference customer。和 LangGraph + Inngest agent kit 直接对位。
⚠ 放弃什么
放弃 vertical RPO 商业化的近期机会;需要做 ontology 抽象、tool registry SDK、多 runtime 适配(不只 Inngest);得和巨头(Anthropic、LangChain、OpenAI)在 agent dev 工具层正面竞争。
💡 为什么值得考虑
v3 三周冲刺出来的几个 pattern(reasoning 参数、diff、reflection、sandbox 五阶段)在同行里真的新,有 dev mindshare 潜力。如果只用来生成招聘 agent 太亏。但承认:这是从'工程师做事'变成'平台公司',资源结构完全不同。
三柱合体,做成'本体驱动的领域 agent 运维平台'(vertical platform)
📌 你在赌
Monitor 已经成熟、Behavior(v3 brain)正在长、Manage 是接下来 8 周的事。坚持三柱合体:用招聘域当锚证明可生产化,用能源/费控当跨域延展,Factory v3 是'本体 → 可运行 agent'的工厂,Monitor 是 fleet 运维,Manage 是治理闸。卖给有多业务域要 agent 化的中大型企业(集团 HR + 财务 + 运营)。
⚠ 放弃什么
时间最长(Manage 几乎没开工、跨域 rule-check 没抽象、多租户基础还没做);风险最大(三柱要一起兑现);也最容易在'什么都做了但都不够好'里打转。
💡 为什么值得考虑
代码里的 IA、ontology generator、per-domain Inngest 隔离、blackboard 监控——所有结构都是按这个方向铺的,不顺着走相当于扔掉 70% 的架构投入。也是唯一能讲'AI 时代企业级 ops platform'故事的方向。但要直面:你现在一个人(或小团队)做一个三柱产品。

如果我是你，这周只做一件事
这周只做一件事:用 v3 brain 真生成一个费控域(或能源域)的真 agent,从 read_ontology 一路到 sandbox 跑通真事件链。不要修 UI、不要拆组件、不要写文档。理由:你最近 3 周已经把 v3 brain 做得很好(reasoning 参数、refine diff、score_spec、FailureReflection),但所有证据都来自招聘域(而招聘 agent 是手写的)和 recruit-gen-v1 测试域(0/6 candidate 的 dryRun)。'v3 能跨域生成 agent' 是 AO 整个三柱叙事的中心点,但这个点目前在代码里没有任何端到端证据。这周跑通(或失败但留下精确的 root cause 进 FailureReflection),你就知道 AO 接下来 3 个月是该深耕招聘、拆 Factory 独立、还是冲三柱合体——三个战略选项目前都靠猜,这次实验给出真信号。如果跑通了,后面再补成本熔断和多租户;如果跑不通,先别建生产化基建,集中算力修推理边界。
